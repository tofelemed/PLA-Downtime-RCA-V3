# TF-PREP-001 Phases 3–8: production database, seed, images and VM scripts

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the first production install of Traverse Forge possible by image swap on the on-prem VM: checksummed SQL migrations applied by script, the Marun HDPE reference data and its 14 accounts seeded from the development database, production-named images and compose, and VM scripts rehearsed end to end on a scratch PostgreSQL 15.

**Architecture:** TypeORM stays the authoring tool; `deploy/db/export-*.sh` turn migrations into `db/migrations/Vnnn__*.sql` (schema `forge`) that `deploy/db/10-migrate.sh` applies through `psql` inside the database container with a checksum ledger. Reference data is extracted from tenant `HDPE-TRAIN` of the dev database by a TypeScript CLI that orders tables by foreign keys and writes plain `INSERT` files (same UUIDs in production). Production runs three containers (`traverse-forge-backend`, `traverse-forge-worker`, `traverse-forge-frontend`) from `deploy/docker-compose.forge.yml` on the private network `forge` plus the database's external network; the bundle (`images + db + deploy`) is built on the dev machine and loaded on the VM.

**Tech Stack:** Bash (Git Bash on the dev machine, Linux on the VM), Docker Compose v2, PostgreSQL 15 (`psql`/`pg_dump` from the `postgres:15-alpine` container), NestJS/TypeORM 0.3 CLIs under `server/pro-act-backend/scripts/deploy/`, Jest.

**Spec:** `deploy/ANALYSIS-REPORT.md` §3–6 (TF-PREP-001 Phase 1), owner answers in `plans/DECISIONS.md` "2026-10-26 — First production installation, TF-PREP-001", variable contract in `deploy/.env.example`, Phase 2 evidence in `deploy/PREP-LOG.md`.

## Global Constraints

- Runtime names (TF-PREP-001 §2): compose project `traverse-forge`; images `traverse-forge-backend:<FORGE_VERSION>` and `traverse-forge-frontend:<FORGE_VERSION>`; containers `traverse-forge-backend`, `traverse-forge-worker`, `traverse-forge-frontend`; private network `forge`; the database's network is external, named by `PG_NETWORK` (default `instrumental-network`); volumes `forge-uploads`, `forge-exports`. Database `traverse_forge`, schema `forge`, RLS role `proact_rls_user` (kept, decision 2026-10-26). Dev compose files, container names and `server/pro-act-backend/` keep their names.
- One existing login (`DB_USER` / `DB_PASSWORD`) does migrations and runtime; it is granted `proact_rls_user`. No `traverse_forge_owner` / `_app` roles.
- Images never migrate or seed at start-up: `DB_MIGRATIONS_RUN=false`. Migrations and seeds are release steps run by the scripts in `deploy/db/`.
- Every `db/**/*.sql` file is listed with its SHA-256 in `db/CHECKSUMS.sha256`; `10-migrate.sh` and `20-seed-reference.sh` refuse a file whose checksum differs from the list, and refuse to re-apply an applied version whose recorded checksum differs.
- SQL in `db/` resolves through `search_path = forge, public`: application objects are `forge.*`; extensions (`uuid-ossp`, `btree_gist`) stay in `public`; no `CREATE ROLE` inside `db/` files (roles are cluster-wide and belong to `00-create-db-and-roles.sh`).
- Seed scope: organisation `MPC-TRAIN`, tenant `HDPE-TRAIN` and every reference (class R) and user (class U) row of that tenant from the dev database `proact` on `proact-postgres` (host port 5432), extracted by script, never hand-copied. Excluded: tenant `HDPE1` / organisation `ASPC`, the tenant-less product `ple1`, class R\* (`integration_connections`, `secrets`, `pi_connections`, `pi_mappings`, `af_bindings`) and every class T table (`deploy/ANALYSIS-REPORT.md` §3.5). Accounts keep their dev password hashes (no forced change, decision 2026-10-26; ruling 2026-10-28).
- Secrets: no real value in the repository; `.env` files are never edited by the agent; scripts read secrets from `/opt/traverse-forge/.env` (VM) or `deploy/.env.local` (rehearsal, git-ignored) and never print them.
- Backend base image stays `node:24-bookworm-slim`, `USER node`. Frontend runtime becomes `nginxinc/nginx-unprivileged:1.27-alpine` listening on 8080. API `PORT=3000` in production compose (code default unchanged).
- Code rules of `CLAUDE.md`: files ≤ 400 lines, functions ≤ 40 lines, no `any`, Nest `Logger` only, named exports, kebab-case files. Shell scripts: `#!/usr/bin/env bash`, `set -euo pipefail`, LF line endings (`.gitattributes` entry `deploy/**/*.sh text eol=lf` and `db/** text eol=lf`), `bash -n` clean.
- Commits end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`. Never push.

## Review Focus

- A migration SQL file edited after it was applied (checksum drift): `10-migrate.sh` must stop with the file name and both checksums, apply nothing (Task 3 test "refuses a tampered applied file").
- `public.` inside the baseline that belongs to an extension function (`public.uuid_generate_v4()`): the rewrite must leave it alone, or every default breaks (Task 2 test "extension members stay in public").
- A self-referencing reference table (`reason_codes.parent_id`): rows must be inserted parents first, or the seed fails half-way (Task 4 test "self-referencing rows load parents first").
- `PI_SERVER` unset in production: `/piwebapi` must answer 404, never proxy to an empty upstream and crash the worker nginx (Task 6 test "piwebapi off without PI_SERVER").
- `load-and-start.sh` with an image tag that is not in the bundle: refuse before touching the running stack, so a typo never leaves the plant without a UI (Task 7 test "unknown version refused").

**Interfaces:**
- `lib.sh`: `forge_load_env <file>` (exports every `KEY=value` line, no echo), `forge_psql <db> [psql args…]` (runs `docker exec -i "$DB_CONTAINER" psql -v ON_ERROR_STOP=1 -U "$DB_USER" -d <db>`; `DB_CONTAINER` default `instrumental-postgres`, password via `PGPASSWORD` env inside `docker exec -e`), `forge_sha256 <file>` (prints the hex digest with `sha256sum` or `shasum -a 256`), `forge_die <msg>` (stderr, exit 1).
- `export-baseline.sh --through <timestamp> --out db/migrations/V001__baseline.sql`: starts `postgres:15-alpine` as `forge-export-pg` on `127.0.0.1:55432`, copies migrations with timestamp ≤ `--through` to a temp dir, runs `npm run migration:run` with `DB_MIGRATIONS_DIR=<temp>` against it, dumps `pg_dump --schema-only --no-owner` (privileges kept: the GRANTs to `proact_rls_user` must survive) plus `pg_dump --data-only --inserts --table=migrations --table=typeorm_metadata`, pipes both through `rewrite-schema.py`, writes the file with the header `-- V001 baseline: TypeORM migrations through <timestamp> (<count> files) exported <date> from <git sha>`, removes the container.
- `rewrite-schema.py` (stdin → stdout, Python 3, no third-party modules): (1) collect `<name>` from every `CREATE (TABLE|TYPE|FUNCTION|PROCEDURE|SEQUENCE|VIEW|MATERIALIZED VIEW|DOMAIN) public.<name>` and every `CREATE … INDEX … ON public.<name>`; (2) replace `public.<name>` by `forge.<name>` for those names only (word boundary; also inside `$$` function bodies); (3) replace `SET search_path = public, pg_temp` → `SET search_path = forge, public, pg_temp` and `to_regclass('public.'` → `to_regclass('forge.'`; (4) replace pg_dump's `SELECT pg_catalog.set_config('search_path', '', false);` by `CREATE SCHEMA IF NOT EXISTS forge;\nSET search_path = forge, public;`; (5) drop `CREATE EXTENSION` lines for `pg_stat_statements` (extensions are created by `00-create-db-and-roles.sh`); (6) `\restrict`/`\unrestrict` and `\connect` lines are removed. Everything else is untouched.
- `verify-schema.sh <db> <schema>`: prints one line per object class (`tables`, `columns`, `indexes`, `constraints`, `functions`, `triggers`, `policies`, `types`, `views`, `sequences`) with the count in that schema, sorted; used to compare the TypeORM-run `public` schema with the `forge` schema built from SQL.
- `checksums.sh`: rewrites `db/CHECKSUMS.sha256` from every `db/**/*.sql` (sorted, paths relative to `db/`, format `<sha256>  <path>`); `checksums.sh --check` exits 1 naming each mismatch.
