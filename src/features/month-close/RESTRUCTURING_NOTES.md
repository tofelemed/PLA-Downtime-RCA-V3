# Stage 2 preparation — month close

Prepared after approval of `docs/FRONTEND_RESTRUCTURING_PLAN.md`. The parent validated the period pilot and authorized Stage 2 implementation. Month close now has the five URL-controlled sections described below. Authentication, API contracts and stored business data remain unchanged.

## Source constraints

- `useMonthClose(month)` makes one tenant-scoped GET `/v2/month-closes/:month`; `current` is resolved by the server. Query identity excludes the proposed section, so section changes must reuse this result without extra reads or commands.
- `month-prerequisites.ts` caps **each** sample at 50. Full pending/proposal counts and total/certified days are separate authoritative fields. Current pending/day text discloses truncation; proposal text does not. New tables must say **First 50 of N shown** (using actual sample length), including proposals. Local sample paging/search must not imply a complete list; use a contained table with `pager="none"` and a bounded height instead of a misleading server pager.
- Pending periods have unit name, operational date, shift and workflow, but no plan ID. Days have unit/date, but no period route. Do not invent links. `/my-queue` accepts only cursor/limit and is scoped to the user's work over a fixed recent window; a plain **Open my queue** link must not promise the selected month's complete backlog or append unsupported filters.
- Proposals have plan ID when available, local date, trigger, reason and creation time; they do not include a unit name. Preserve the existing `/plans/:planId/periods/:periodId` link only when plan ID exists. Show no raw unit UUID or guessed unit name. The period pilot keeps the base bookmark compatible.
- Month keys and deadline dates come from the server, including Solar Hijri financial months. Display dates through existing calendar preferences and `PlantTime`; do not calculate financial month boundaries or due dates in the browser.
- `CloseActions` already enforces lifecycle/capability presentation, quantity-signer exclusion, prerequisite/materiality disabled states and locked-month immutability. Backend policy-specific role checks remain authoritative. Keep `useMonthCloseStep`, payloads, idempotency and existing dialogs; only one mounted `CloseSignOffs` owns these commands.

## Implemented composition

1. `model/close-section.ts`: whitelist `overview|periods|days|proposals|history`; absent/invalid section displays overview without an automatic navigation/write. A small search-parameter helper copies the existing parameters and sets only the changed key.
2. `components/close-section-nav.tsx`: existing Radix tabs with URL-controlled value, an accessible Month close sections label, wrap-friendly triggers and visible focus. User section selection pushes history. Preserve month and all unrelated query keys; month navigation preserves section. Back/Forward and refresh read the URL.
3. `components/close-overview.tsx`: three authoritative prerequisite counts as section links; responsive desktop columns place existing deadlines/materiality next to the single sign-offs component. On desktop, sign-offs appear in the first screen instead of after 150 rows. Mobile stacks these groups without whole-page horizontal overflow. Count/status language distinguishes policy-disabled blockers from satisfied blockers.
4. `components/close-prerequisites.tsx`: convert the three lists into cohesive section tables (periods: date/unit/shift/workflow; days: date/unit; proposals: date/trigger/reason/created/period link). Do not add secondary requests to resolve absent fields. Explicitly disclose capped samples and unavailable sample rows when a positive count has an empty sample.
5. `CloseHistory`: show audit entries directly inside its dedicated section; give empty history an explicit empty state. It remains read-only. Do not require opening a second History disclosure after selecting History.
6. `month-close-page.tsx`: retain Page/Header/MonthNav/DataState and the existing hook. Choose the visible section under the URL-controlled tabs. Keep `close-prerequisites`/`data-met` on the overview summary where existing read-only acceptance checks need it; stable existing action/sign-off test IDs remain.

The command dialogs live only on Overview. Do not automatically save a comment or execute a close when switching sections/months. Month/section navigation must not silently move an already-open confirmation to another month: reset or key the command owner by `view.monthKey`, and verify the submitted path still targets the month named by the dialog. Existing confirmation focus and pending protection remain intact.
