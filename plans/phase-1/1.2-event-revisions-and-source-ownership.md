# 1.2 Event revisions and source ownership

**Status:** ⬜ not started · **Epic:** P1 E03 · **Spec:** ING01 duplicates/corrections/retractions, ING06 source vs user layers, §5.3 conflicts, DT11, WF04 (late corrections), §14.2 `event_revisions`, `event_coding`, G02 · **Tests:** T04 · **Depends on:** 1.1

## Goal
Separate what the source says from what the user decided. A PI update may change raw timing and attributes; it must never reset status, codes, comments, RCA links or overrides (I1/B5). Every change is an immutable revision with provenance, and retractions tombstone rather than delete.

## Spec requirements covered
- ING01: distinguish duplicate delivery, correction, retraction, independent observation; retraction tombstones and triggers affected-period reevaluation; never deletes approved history.
- ING06: source facts, user coding, approved accounting are separate layers; source updates cannot reset workflow/user fields; overrides record author, time, old, new, reason, overridden source revision.
- §5.3: source correction vs override conflict → show both, create review item; change affecting approved period → proposed accounting revision (consumed in 2.8).
- DT11: coding state transitions; §14.2 `event_revisions` (immutable revision per event), `event_coding` (explicit effective coding revision).
- WF04 hook: late corrections enter raw storage; drafts recalc; approved → proposal.

## Current implementation (verified)
- `pi-event-pull.service.ts` builds a full DTO with `status: 'Open'` and calls `update()` on existing events (B5) — user coding and status are overwritten; manual edits to mapped fields lost.
- `production_events.audit_trail` text column holds ad-hoc JSON of field changes (frontend-written).
- No revision table; no concept of source vs effective values; no retraction.

## Target design
**Schema (migration `0003-event-revisions`)**
```
event_revisions
  id, tenant_id, event_id FK, revision int, kind enum(source, user, system, retraction),
  source_facts jsonb        -- start, end, raw attributes, source_revision, raw_observation_id (1.5)
  effective_facts jsonb     -- what the event looks like after this revision (materialized snapshot)
  change_reason text, actor_id uuid null, actor_kind enum(user, connector, system),
  source_revision varchar null, created_at
  UNIQUE (event_id, revision)
event_coding
  id, tenant_id, event_id FK, revision int, 
  reason_code_version_id, impact_code_version_id, oee_code_version_id (FK to versioned codes from 1.3; nullable until 1.3 lands → plain code ids first),
  schedule_class, oee_component, impact_mode, impact_fraction, comment,
  is_override bool, overrides_source_revision int null, old_values jsonb, new_values jsonb, reason text,
  author_id, created_at
  UNIQUE (event_id, revision)
event_review_items
  id, tenant_id, event_id, kind enum(source_vs_override_conflict, late_correction, retraction), 
  source_revision_id, coding_revision_id, state enum(open, kept_override, accepted_source, dismissed), resolved_by, resolved_at
production_events: current_source_revision int, current_coding_revision int, retracted_at null
```
**Rules in `EventRevisionService`**
- `applySourceRevision(eventId, sourceFacts, provenance)`:
  1. Compare with current `source_facts`; identical content (hash) → record duplicate in raw layer only (1.5), **no revision** (ING01).
  2. Changed → insert `event_revisions(kind=source, revision=n+1)`; update **only** source-owned columns on `production_events` (`start_time`, `end_time`, `legacy_end_sentinel`, raw attribute columns that have no user override); never touch `coding_state`, `rca_state`, `rca_id`, `description` if user-edited, codes, comments.
  3. If a user override exists on a field the source changed → `event_review_items(source_vs_override_conflict)`; effective value stays the override.
  4. Emit `EventChanged` (outbox, 1.5) with affected interval → Phase 2 recalculation; if the event touches an approved period → `PeriodRestatementProposed` (2.8).
- `applyUserCoding(eventId, codingDto, actor, ifMatch)`: new `event_coding` revision; `coding_state` → coded; `is_override` when the field has a source value; stores old/new/reason.
- `retract(eventId, sourceRevision)`: `physical_state=retracted`, `retracted_at`, revision `kind=retraction`; accounting reevaluation event; never delete.
- `effective(event)` = source facts overlaid by current coding revision; served by v2 `GET` with both `source` and `effective` blocks (UX: "source/effective value comparison" in 3.2).
- v1 PI pull (`pi-event-pull.service.ts`) is changed to call `applySourceRevision` instead of `update` (bridge until 1.6 replaces the adapter).

**API v2**
- `GET /api/v2/production-events/{id}` → `{effective, source, revisions[], coding[], reviewItems[]}`.
- `PATCH /api/v2/production-events/{id}` (user fields) → coding revision; `If-Match` = `row_version`.
- `GET /api/v2/production-events/{id}/revisions`; `POST /api/v2/event-review-items/{id}/resolve {decision: keep_override|accept_source}`.

## Tests
- **T04 source refresh** (integration): create PI-sourced event; user codes reason + links RCA (`rca_state linked`); apply source revision with new end time → end updated, revision 2 recorded, coding/RCA/status unchanged; `GET` shows both.
- Duplicate source content → no new revision, duplicate counter incremented.
- Override conflict → review item open; resolve `accept_source` replaces coding field and records provenance; `keep_override` keeps.
- Retraction → `physical_state retracted`, `EventRetracted` emitted, event excluded from downtime union (1.1 service).
- Concurrency: two `PATCH` with same `If-Match` → second gets 412.

## Definition of done
- Revisions and coding tables live; PI re-sync preserves user work (T04 green); v2 detail exposes source vs effective; outbox events emitted; B5/I1 marked resolved in `plans/evidence/s1-verification.md`.

## Decisions / risks
- Storing `effective_facts` as a snapshot per revision costs space but makes "reproduce any approved total" (§1) cheap; accepted.
- Until 1.3 delivers versioned codes, `event_coding` stores plain code ids; a follow-up migration adds version FKs.
