# 1.4 Event operations — split, merge, bulk-code, close

**Status:** 🧪 implemented 2026-10-08; unit + integration green (T37 and companions); CI run pending · **Epic:** P1 E03 · **Spec:** DT08–DT11, API02 idempotency/If-Match, API04 async jobs, §15.2 event command routes, §14.2 `event_relations` · **Tests:** T37 · **Depends on:** 1.1, 1.2

## Goal
Give operators the editing operations downtime analysis needs — split a stop when the cause changed, merge fragments, code many events at once, close an open stop — as atomic, idempotent, revisioned server commands that preserve lineage and trigger recalculation.

## Spec requirements covered
- DT09: split at a timestamp strictly inside; children keep provenance + parent id; original superseded for accounting. Merge requires same tenant/scope, compatible classifications, adjacent/overlapping under gap policy; preserve contributing ids. Both recalc drafts and create restatement proposals for approved periods; never edit source evidence.
- DT10: bulk coding preview (ids, before/after, count, exclusions, period impact); optimistic versions; ≤500 atomic, larger → async job with per-chunk outcomes and partial status. Close-open-stop needs end + reason; closing a source-owned event creates an override until source confirms.
- DT11: operations change physical/coding state only; closing ≠ approving.
- API02: `Idempotency-Key`, `expectedVersion`/`If-Match`; 409/412 semantics. API04: 202 + job for large batches.
- §14.2 `event_relations`: parent/child or correlated, relation type, occurrence_id, confidence, approval; no cycles; same tenant.

## Current implementation (verified)
- None of split/merge/bulk-code/close exists (UI or API). `common/dto/bulk-operations.dto.ts` exists unused. Event Hub "close" = set status manually.

## Target design
**Schema (migration `0005-event-relations`)**
```
event_relations: id, tenant_id, from_event_id, to_event_id, relation_type enum(split_child_of, merged_from, correlated_with, impact_of), occurrence_id uuid null, confidence numeric(5,4) null, approved_by null, created_at
  CHECK from_event_id <> to_event_id ; UNIQUE (from_event_id, to_event_id, relation_type)
production_events: + occurrence_id uuid (physical stop occurrence; split children share it → KPI06 count stable), superseded_by_event_id null
bulk_jobs: id, tenant_id, kind enum(bulk_code, ...), state, total, processed, failed, chunks jsonb, requested_by, created_at, finished_at
```
**Commands (`EventCommandService`, each in one transaction)**
- `split(eventId, splitAt, reason, expectedVersion)`: validate `start < splitAt < effectiveEnd` (open event: `splitAt < now`); create two children (`source_kind` = parent's, `occurrence_id` = parent's, coding copied, revisions `kind=system` with reason), relations `split_child_of`, parent `physical_state=superseded`, `superseded_by` null (two children) — accounting reads children only. Emits `EventChanged` for the parent interval.
- `merge(eventIds[], expectedVersions[], gapPolicy, reason)`: same tenant, same unit, compatible `physical_type`/`schedule_class` (or explicit override), intervals adjacent/overlapping within `gapPolicy.maxGapSeconds` (default 0); new event spanning union; contributors superseded; relations `merged_from`; occurrence_id = earliest contributor's; coding from the first unless conflicting → 422 with conflict list.
- `bulkCode({ids, versions, codes, reason, preview})`: preview returns before/after per id, exclusions (superseded/retracted/stale version/foreign scope) and impacted periods (from 2.x once available; before that: affected windows); apply ≤500 atomic via `applyUserCoding` (1.2); >500 → `bulk_jobs` processed by worker in chunks of 200 with per-chunk result; final state `completed|partial|failed`.
- `close(eventId, endTime, reason, expectedVersion)`: `end > start`; manual event → source facts end set (user revision); source-owned → coding override `end_override` recorded, effective end = override until a source revision confirms (then review item auto-resolved if equal).
- All commands: `@Idempotent()`, `expectedVersion` → 412 on mismatch, 409 on invalid state (e.g. split a retracted event).

**API v2** (§15.2): `POST /production-events/{id}/split`, `POST /production-events/merge`, `POST /production-events/bulk-code` (`preview: true|false`), `POST /production-events/{id}/close`, `GET /jobs/{id}`.

## Decisions / risks
- Gap policy default 0 s (strict adjacency); configurable per tenant policy (0.2 `state_rules`).
- Period-impact preview in bulk coding depends on 2.x; until then report affected time windows.
- **Deviations (8 Oct 2026, implementation):**
  - **Request shapes:** single-event commands (split, close) take the version from `If-Match` (428/412 like PATCH) instead of a body `expectedVersion`; merge and bulk-code take `events`/`items` = `[{eventId, expectedVersion}]` instead of parallel `eventIds[]` / `expectedVersions[]` arrays. Merge `overrideClassification: true` is the "explicit override" (earliest event's physical type/schedule class kept).
  - **Bulk codes** are the PATCH coding fields `reasonCodeId`, `scheduleClass`, `oeeComponent` (a reason brings its rule/default classification, plan 1.3; an existing impact code is never replaced). Atomic apply refuses the whole batch on any exclusion: 404 (unknown/foreign), 409 `INVALID_STATE`, 412 `STALE_REVISION`, 422 `DUPLICATE_EVENT`, with `details.exclusions`. Jobs check scope and repeated ids when accepted (404/422); versions and states per chunk (a failed chunk records its error code). Request cap 10 000 items. `affectedWindows` (per unit, merged) stand in for period impact until 2.x.
  - **Amounts:** split prorates `quantity`/`cost` by duration (open parent: all on the running child), merge sums them, so totals are conserved across split/merge (engineering default, DECISIONS §D).
  - **Coding conflicts in a merge** compare reason/impact/OEE codes, OEE component, impact mode/fraction, quantity unit and RCA link; a null never conflicts; the merged event takes the first non-null value in start order. Description, event type, asset, plan come from the earliest contributor.
  - **Business id:** derived events get `<eventId>#1`, `#2` (split) or `#m` (merge) so the source id keeps pointing at the source record; a later source revision for a superseded event stays on it (source evidence never moved) and opens a `late_correction` review item.
  - **Superseded events:** legacy status `Cancelled`; any user change (v1 PUT, v2 PATCH) → 409 `INVALID_STATE`. Derived events carry no source revision of their own (`sourceFacts` null).
  - **Close:** `endTime` must be after the start and not in the future (422 `CLOSE_END_BEFORE_START` / `CLOSE_END_IN_FUTURE`); a closed event → 409 `EVENT_NOT_OPEN`. Auto-resolution sets the item to `accepted_source` with `resolved_by` null; `accept_source` on a pending item uses the latest source end.
  - **Idempotency:** the interceptor now stores the status the handler set (bulk-code answers 200 or 202 on one route), so a replayed job acceptance is 202.
  - **Roles:** no extra role beyond tenant membership, as v2 PATCH (operations UI and role gating in 3.2).
  - Size rules: `production-event.entity.ts` (+11 lines, already > 400) and `source-revision.ts` `applySourceIn` (45 lines) slightly over; new functions ≤ 40 lines.
- **Open (follow-up):** no restatement proposals for approved periods (2.8) and no Phase 2 consumer (2.5) — messages are logged/broadcast only; bulk jobs stuck in `running` after a worker crash are not re-queued (needs a lease/heartbeat, 1.5 job runner); per-event code-default lookups in bulk coding are 2 queries per event (fine at 500, batch them if jobs grow); `correlated_with`/`impact_of` relations, confidence and approval have no writer yet; operations UI is 3.2.
