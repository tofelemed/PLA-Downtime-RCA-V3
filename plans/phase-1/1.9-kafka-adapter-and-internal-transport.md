# 1.9 Kafka adapter and internal transport

**Status:** ⬜ not started · **Epic:** P1 E06 · **Spec:** KF01–KF05, FND02, §4.1 Kafka as internal transport, API05 realtime from outbox, D10 · **Tests:** T10; T23 (transport half) · **Depends on:** 1.5 (outbox/inbox)

## Goal
Two things with one client stack: (1) a certified Kafka **source** adapter that consumes approved topics with exactly-once business effects via the inbox, and (2) the **internal transport** (`pla.*.v1` topics) fed by the outbox relay and consumed by the realtime gateway, accounting recalculation and downstream delivery.

## Spec requirements covered
- KF01 approved topics, consumer group, TLS + SASL/mTLS, ACLs, schema registry ref, payload format, max record size, offset start policy; never reset offsets silently; replay = named job + audit.
- KF02 preserve topic/partition/offset/key/time/headers; ordering per partition; key by tenant + source object; inbox unique key + transactional domain write; commit offsets after durable processing; rebalance handling.
- KF03 JSON/Avro/Protobuf decoders; versioned canonical schema; compatibility rules; unsupported → quarantine.
- KF04 internal topics `pla.raw.v1`, `pla.normalized.v1`, `pla.event.changed.v1`, `pla.period.recalculate.v1`, `pla.period.approved.v1`, `pla.deadletter.v1`; large payloads (>1 MiB) to object storage with reference + hash; prod RF 3 / acks all / min ISR 2 / idempotent producers.
- KF05 raw replay retention independent of Kafka retention; dead-letter records with coordinates/schema/error/lineage; poison records quarantined without blocking valid ones; completeness alarm per affected period.
- FND02 at-least-once + idempotent; API05 emit once per outbox id.

## Current implementation (verified)
- No Kafka client in the backend (`kafkajs` not a dependency). `streaming` module stores Kafka-like config only. Docs describe a Telegraf/Kafka architecture that was never built.
- Host has `instrumental-kafka-1..3` (cp-kafka 7.5.0) + Zookeeper + `kafka-ui`, stopped, on `instrumental-network`.

## Target design
**Client**: `kafkajs` (or `@confluentinc/kafka-javascript`); one `KafkaModule` providing producer (idempotent, `acks: -1`) and consumer factory; config from env (`KAFKA_BROKERS`, `KAFKA_SASL_*`, `KAFKA_TLS`).

**Source adapter `KafkaSourceAdapter implements Adapter`**
- Config: `topics[]`, `groupId` (per connection), `decoder enum(json, avro, protobuf)`, `schemaRegistryUrl`, `payloadMapping` (same schema as MQTT), `maxRecordBytes`, `offsetStartPolicy enum(committed_only, earliest_once_on_create, timestamp)` — any change of start policy requires an explicit replay job (KF01).
- `eachMessage`: decode → envelope with provenance `{topic, partition, offset, key, timestamp, headers}` and `message_id = ${topic}-${partition}-${offset}`; `inbox.delivery_key` = same; `IntakeService.accept()` in the same transaction as inbox insert; **commit offset only after commit** (manual `commitOffsets`). Decode/schema failure → `pla.deadletter.v1` + `ingestion_exceptions(schema_invalid)` and offset advances (poison does not block, KF05) with `completeness=false` alarm.
- Rebalance: `consumer.on('group.join')`/`rebalancing` → finish or abort in-flight batch; resume from committed offsets (T10).
- Replay: `POST /connections/{id}/replays {fromTimestamp|fromOffsets}` → new consumer group `…-replay-{runId}` reading the range; envelopes tagged `replayRunId`, identity unchanged → duplicates recognised.

**Internal transport**
- `OutboxRelay` (1.5) publishes `outbox` rows: `type → topic` map (`EventChanged→pla.event.changed.v1`, `RawAccepted→pla.raw.v1`, `Normalized→pla.normalized.v1`, `PeriodRecalculateRequested→pla.period.recalculate.v1`, `PeriodApproved/Restated→pla.period.approved.v1`), key = `tenantId:aggregateId`, headers `schemaVersion, domainEventId, correlationId`; payload >1 MiB → object store ref + sha256.
- Internal consumers use the `inbox` helper: realtime gateway (3.1 completes scoped rooms; transport test T23 here), accounting worker (2.5), downstream delivery (2.9).
- Topic provisioning script (`scripts/kafka/create-topics.ts`) with dev (RF 1) and prod (RF 3, min ISR 2) profiles; retention 7 d raw (§17.1).
- Dead-letter viewer via `GET /ingestion-exceptions?errorCode=schema_invalid` + `pla.deadletter.v1` coordinates.

**Dev infra**: Compose `kafka` single-broker KRaft (cp-kafka 7.5) + optional `kafka-ui`; override to reuse `instrumental-kafka-*`.

## Tests
- **T10 Kafka crash** (integration with real broker): consumer commits DB (inbox + accept) then crashes before offset commit; restart + rebalance → redelivery → inbox unique key prevents second effect; no accepted record missing; offsets end committed.
- **T23 (transport)**: `EventChanged` published once per outbox id even when relay retries; consumer dedupes by `domainEventId`.
- Poison record (invalid JSON) → dead-letter + exception; subsequent valid records processed; alarm flag set for scope.
- Offset policy change without replay job → 409; replay job reads range with new group, duplicates recognised, audit row written.
- Large payload → reference + hash; consumer resolves reference.
- Rebalance mid-batch → no duplicate business effects, no skipped offsets (two consumers join/leave during load).

## Definition of done
- Kafka source adapter certified against the matrix; internal topics live with outbox relay; realtime and accounting consumers can subscribe; D10 defaults recorded.

## Decisions / risks
- `kafkajs` is mature but community-maintained; the Confluent JS client is the alternative — decide in step 1 by a spike against cp-kafka 7.5.
- Schema registry is optional in dev (JSON); Avro/Protobuf decoders are capability-flagged and may slip to R2 if no source needs them (KF03 still requires versioned canonical schema, which 1.5 provides).
