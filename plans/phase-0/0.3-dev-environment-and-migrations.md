# 0.3 Dev environment, migrations, worker process, CI

**Status:** ⬜ not started · **Epic:** P0 E02 (enabler) · **Spec:** §4.1 (API + worker), §14.1 DB01–DB03, §18.1 MIG02 (expand-and-contract), §19.3 test layers, NFR07 · **Tests:** migration round-trip; CI pipeline green · **Depends on:** 0.1

## Goal
Make it possible to build the rest of the plan safely: schema changes through versioned migrations instead of entity sync, a worker entrypoint for connectors and calculations, Kafka and MQTT available in Compose, and a CI pipeline that runs unit, integration (real Postgres), contract and e2e tests.

## Spec requirements covered
- §4.1: "one domain codebase with separately deployable API and worker processes".
- MIG02: expand-and-contract migrations, compatibility adapters, feature flags.
- DB01–DB03 conventions enforced from the first new migration (UUID PK + `tenant_id`, `(tenant_id, id)` unique pairs, audit columns, `row_version`, checks, composite indexes starting with tenant).
- §19.3: unit, contract, integration with real persistence/messaging, e2e, resilience/load/authz layers.
- NFR07: health/readiness, graceful drain (worker), tested infrastructure definition.

## Current implementation
- `app.module.ts`: `TypeOrmModule.forRoot({ type: 'postgres', synchronize: process.env.DB_SYNCHRONIZE === 'true' })`; no `migrations` config, no data-source file, no CLI scripts. `TableInitService` is a no-op on Postgres.
- Legacy `.sql` files in `migrations/` and `database-setup/` are MSSQL and unused.
- One process (`main.ts`); `@nestjs/schedule` cron runs inside the API process (PI scheduler).
- Compose: `frontend` (nginx), `backend`, `postgres` (bundled, 5433) + override for `instrumental-postgres`. No Kafka/MQTT/worker services. Host already has `mosquitto` running and `instrumental-kafka-1..3` + `instrumental-zookeeper` (cp 7.5) stopped on `instrumental-network`.
- Tests: Jest with `rootDir: src`, `testRegex: .*\.spec\.ts$`; no integration DB harness; Playwright config starts both servers.
- Backend Dockerfile exists (`server/pro-act-backend/Dockerfile`, compiles `dist/scripts`).

## Target design
**Migrations**
- `server/pro-act-backend/src/database/data-source.ts` exporting a TypeORM `DataSource` for CLI (reads `.env`), `migrations: ['dist/database/migrations/*.js']` in app config, `migrationsRun: true` on boot behind `DB_MIGRATIONS_RUN` (default true), `synchronize: false` everywhere.
- Scripts: `migration:generate`, `migration:run`, `migration:revert`, `migration:show`.
- Initial migration `0001-baseline` generated from the current entities against an empty DB, then verified against the live `proact` DB with `migration:show` (should report nothing pending) — this freezes the current schema as version 1.
- Convention doc `server/pro-act-backend/src/database/MIGRATIONS.md`: expand (add nullable/new tables) → backfill job → switch reads behind flag → contract (drop) in a later release; every migration has `down`.
- Shared base entity `TenantScopedEntity` (`id uuid`, `tenant_id uuid`, `created_at`, `created_by`, `updated_at`, `updated_by`, `row_version int` with `@VersionColumn`) used by all new tables (DB01).

**Worker**
- `src/worker.ts` bootstrap: `NestFactory.createApplicationContext(WorkerModule)`; `WorkerModule` imports the same domain modules plus `ScheduleModule` and connector modules; API process sets `RUN_SCHEDULERS=false` so cron jobs run only in the worker. Graceful shutdown hooks (`enableShutdownHooks`) drain in-flight jobs (ING02 "stop means finish or persist in-flight work").
- `package.json`: `start:worker`, `start:worker:dev`; Dockerfile `CMD` selectable via `PROCESS_ROLE=api|worker`.

**Compose (dev)**
- Add `worker` service (same image, `PROCESS_ROLE=worker`), `kafka` (single broker KRaft, cp-kafka 7.5 to match the existing cluster image, or reuse `instrumental-kafka-*` via the external network override), `mqtt` (eclipse-mosquitto, or reuse host `mosquitto`), `kafka-ui` optional.
- `.env.example` gains `KAFKA_BROKERS`, `MQTT_URL`, `RUN_SCHEDULERS`, `DB_MIGRATIONS_RUN`.

**CI (GitHub Actions or local `npm run ci`)**
- Jobs: `lint` → `unit` (backend Jest, frontend Vitest) → `integration` (Postgres service container; Jest project `test/integration` with `testRegex .*\.int-spec\.ts$`, Testcontainers or service container) → `contract` (OpenAPI snapshot diff for v2) → `e2e` (Playwright against Compose). Fixture tests from 0.1 run in `unit`.
- Jest projects config: `unit` (src), `integration` (test/integration), `fixtures` (test/fixtures).

## Decisions / risks
- Choice between bundled Kafka in Compose vs reusing `instrumental-kafka-*` (D10): default bundled single-broker for isolation; override file for the shared cluster.
- Baseline migration from a DB that was itself produced by `synchronize` may differ cosmetically from entity metadata (e.g. FK names). Resolve by generating from entities, not from the DB.
