# 0.2 Decision register and proposed policies

**Status:** ⬜ not started · **Epic:** P0 E01 · **Spec:** §21 D01–D15, §3.1–3.3, §9, §11.3, §12, §13.2 · **Tests:** none · **Depends on:** — (parallel with 0.1)

## Goal
Turn every site-specific policy the spec leaves open into a recorded decision with an owner, a **proposed default we build against now**, and the commissioning gate at which the owner must confirm it. Unresolved defaults become visible configuration, never a reason to omit a feature (§21).

## Spec requirements covered
- §21 decision table D01–D15; §21.1 definition of done; §21.2 traceability convention.
- Policy-bearing requirements that need a default to implement: ACC09 tolerance, KPI02 planned stops, DT02 debounce/micro-stop, CAL01 operational day, VAL01 margin vs cost, WF02 separation of duties, SRC01 authority, ACT05 coverage gate.

## Current implementation
- No policy objects exist. The closest are `rca_trigger_configs.globalSettings` (JSON), `dashboard_configurations.widget_config` (OEE weights, `lossValuePerUnit` 100, thresholds) and `rca_analysis_configs`. None are versioned or approved.
- `tenants.timezone` exists, never read. Shifts are free text.

## Target design
1. `plans/DECISIONS.md` — the living register (mirrors the table in `plans/README.md`, with discussion notes and confirmation evidence).
2. A **policy model** in the backend (built in 2.x, designed here): `accounting_policies` (tenant/site/unit scope, `policy_kind`, JSON body validated by schema, `version`, `effective_from/to`, `approved_by/at`). Kinds: `reconciliation_tolerance`, `oee_policy`, `coverage_gate`, `state_rules`, `valuation_basis`, `source_authority`, `approval_roles`. Every calculation run records the policy versions it used (FND03, WF03).
3. Proposed defaults (to be built as seed policies):

## Steps
- [ ] 1. Create `plans/DECISIONS.md` with the table above plus "Discussion" and "Confirmed by / date / evidence" columns.
- [ ] 2. For each decision, list the sub-phases whose schema or logic depends on it (so a change triggers a known review list).
- [ ] 3. Define the `accounting_policies` JSON schemas (one per `policy_kind`) in `contracts/policies/*.schema.json`; include the defaults above as `default.json` per kind.
- [ ] 4. Review with the product owner; record answers or "default accepted for now" per row.
- [ ] 5. Update `plans/README.md` decision table statuses.

## Tests
- Schema validation test: each `default.json` validates against its policy schema (runs in CI from 0.3).

## Definition of done
- Every D01–D15 row has owner, default, gate, dependent sub-phases; policy schemas and defaults committed; product owner review recorded.

## Decisions / risks
- The product owner may not be able to answer D03–D06 immediately; the plan proceeds on defaults and the policy model makes later changes a versioned configuration change, not a rewrite.
