# 3.8 Codes, profiles and declarative admin rules

**Status:** 🧪 implemented 2026-10-10 (T18 UI and T22 Playwright green, T22 restart / replay integration-tested; finance policy screens not in this plan — see decisions) · **Epic:** P3 E10 · **Spec:** §16.2 rows "CodesManagement and reason tree", "AdminPanel.tsx"; §3.2 code libraries; NFR02 declarative rule grammar (no `new Function`/eval); T18 (UI), T22 · **Tests:** T18 UI e2e; T22 rule persistence/replay · **Depends on:** 3.1, 1.3

## Goal
Make the code libraries truly manageable — persisted reason hierarchy with versions and effective dates, tenant scope, default OEE/schedule mappings with preview, retirement impact — and replace the executable browser status rules with a server-side declarative rule engine with validation, version history, simulation and rollback.

## Spec requirements covered
- §16.2 CodesManagement/reason tree: persist hierarchy, tenant scope, effective versions, OEE/default mapping preview, retirement impact. AdminPanel: declarative rule builder with validation, version history, simulation, rollback; server rule engine.
- NFR02: allowlisted fields/operators, bounded execution cost, version control, simulation step.
- §3.2 reason/impact/OEE distinct; failure code groups; GE impact codes preserved where required.
- T22: save declarative rule → restart → replay fixture → same result; no function serialization or arbitrary code.

## Current implementation (verified)
- `CodesManagement.tsx` loads all tenants' codes; reason tree UI (`ReasonCodeLibraryTree.tsx`) builds hierarchy from `parentId` that the backend rejects (B12); no versions/effective dates; loss categories hard-coded. `AdminPanel.tsx` edits status automation rules as `new Function(conditionBody)` saved to `localStorage`, losing functions on save (B15); `EventHub.tsx` evaluates them client-side.

## Target design
**Codes UI** `features/master-data/codes/`: tenant-scoped lists (no cross-tenant rows), reason tree with drag-reparent (server validates cycles), node editor (code, name, category, `default_oee_component`, `default_schedule_class`, default impact, effective from/to), version history per node, **retire** with impact dialog (counts of events/lines/rules referencing; 409 details from API), mapping preview ("events coded with this reason in the last 30 days would be classified as …"); impact codes with valuation link indicator (2.6), OEE codes, failure code groups (class/problem/cause/remedy tabs), loss category definitions; GE impact code seed set optional per tenant.

**Rule engine (server)** — migration `0018-rules`:
```
rules: id, tenant_id, kind enum(coding_default, status_derivation, rca_trigger_hint, validation), version, state enum(draft, active, retired), effective_from/to, definition jsonb, created_by, approved_by
rule_runs (simulation): id, rule_id, version, sample_scope, results jsonb, ran_at
```
`definition` grammar (JSON, schema-validated): `{ when: { all: [ {field, op, value} ], any: [...] }, then: [ {set: field, value} | {flag: code} ] }` with **allowlisted fields** (event physical type, schedule class, codes, duration seconds, unit/asset tags, source kind, attributes by name) and **operators** (`eq, neq, in, gt, gte, lt, lte, exists, matches(glob)`); max 20 conditions, no nesting beyond 2, evaluated by a pure interpreter with a step budget. Applied server-side by `EventClassificationService` (1.1) on create/revision; results recorded as `system` coding revisions with `rule_version`. Status labels for v1 derive from states (1.1), so the old "status rules" become `status_derivation` display rules only.
`POST /rules/{id}/simulate {from,to,unitIds}` → before/after counts and sample diffs; `POST /rules/{id}/activate` (version increments; previous retained), `POST /rules/{id}/rollback {toVersion}`.

**Admin UI** `features/admin/rules/`: builder with field/operator pickers from `GET /rules/schema` (allowlist), live validation errors, simulation panel, version timeline with diff and rollback; no free-text code input anywhere.

## Decisions / risks
- Drag-reparent affects `path` of a subtree; server recomputes paths in a transaction; large trees fine (hundreds of nodes).
- **Implemented 2026-10-10 — deviations and open points (engineering defaults, not yet reviewed by the owner):**
  - *Contract changes (flagged; OpenAPI snapshot: 17 operations added, none removed):* the 11 `/v2/rules` operations, `GET /v2/{reason-codes|impact-codes|oee-codes|failure-code-groups|loss-category-defs}/{id}/references`, `GET /v2/reason-codes/{id}/mapping-preview`. Behaviour changes on existing routes: code library writes (create / change / retire) and `POST /v2/code-mapping-rules` now need a tenant-wide grant (403 `TENANT_SCOPE_REQUIRED` for a unit-limited writer — codes are tenant-wide master data); the v2 event view's `classificationBasis.<axis>.source` gains the value `declarative_rule`. Migration `DeclarativeRules1793052800000` (new tables + one index on `production_events`).
  - *Schema shape:* the plan's single `rules` row per version became `rules` (identity, kind, state, version in force, editable draft) + immutable `rule_versions` (activation and rollback only add rows; nothing is rewritten) + `rule_runs`; a version's `effective_from` is its activation time; there is no future-dated activation.
  - *Application scope in R1:* only `coding_default` rules change data, and only on **v2 event create**, filling axes nobody set (precedence user > reason-code mapping rule / default > declarative rule > event-type default). Not applied on PATCH, on PI / intake creates, or as `system` coding revisions (the basis is recorded in `classification_basis` instead). `status_derivation`, `rca_trigger_hint` and `validation` rules are stored, validated and simulated only — their consumers are the state engine (1.10), the RCA trigger service (3.9) and the review queue; anything 1.10 would consume is out of scope beyond storage / validation.
  - *Grammar:* event attributes by name are not in the allowlist (source facts live on revisions, not on `production_events`, so a simulation could not read them); the facts are the event columns listed by `GET /rules/schema`. Separation of duties: the draft author cannot activate; a rollback re-approves an already approved definition and needs a manager approver (no SoD check). Simulation shows the rule in isolation (user values and reason defaults are not layered on). Live validation reports semantic errors only once the definition passes the JSON schema (an incomplete action row first shows its schema error).
  - *T22 "restart backend":* proven in the integration test (the Nest app is closed and booted again on the same database; simulation and new events give identical results). The Playwright spec replays the same events through version 1 twice instead of restarting the owner's running API.
  - *Codes UI gaps:* failure code groups are one tree with level badges (class → problem → cause → remedy) instead of four tabs (tabs would hide the hierarchy); the GE impact code seed set is not offered (no API); asset conditions in rules take an asset id (no v2 asset list yet; the server checks it); a code mapping version starts at save time (no effective-from picker), so earlier events keep their basis; v1 code create / edit (Master Data) still does not append `code_versions` (lazy baseline on the first v2 change, 1.3 open point) — left as is because the v1 screens stay for flag-off plants (C4).
  - *Finance policy screens:* FX rates (`/v2/fx-rates`) and valuation policies (`/v2/valuation-policies`) still have no UI. This plan covers code libraries and declarative rules, not accounting-policy administration, so they were not built here; they belong with a finance / policy administration screen (proposed as a 3.10 cutover prerequisite, since valuation stays `policy_unapproved` until finance approves the v2 IRR + USD policy — the owner's decision, untouched). D06 approval roles stay constants in code (`approval_roles` is not stored).
  - *Bundle:* `new Function` is gone from the Admin Panel chunk; the only remaining occurrence in the production bundle is the v1 Connectivity chunk (`BaseConnector` user filter / transform functions of the legacy connector framework, flag-off plants only) — to be removed with the v1 Connectivity screen (3.10).
  - *Size rules:* the `ProductionEventsV2CommandService` constructor grows to 6 injected services (was 5, already over the limit); `openapi-v2.spec.ts` grows by 14 lines (stubs); `declarative-rules.int-spec.ts` is 417 lines after formatting (helpers in `support/rules-world.ts`).
