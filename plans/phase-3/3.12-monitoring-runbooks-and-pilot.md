# 3.12 Monitoring, runbooks, recovery drill and pilot acceptance

**Status:** ⬜ not started · **Epic:** P3 E12 · **Spec:** NFR04–NFR07, §17.1 recovery/buffering/retention, MIG03 pilot, MIG06 release evidence, §19.3 release evidence, §21.1 definition of done, T39 · **Tests:** T39 restore + outbox replay; alert/runbook rehearsal; pilot acceptance record · **Depends on:** 3.10, 3.11

## Goal
Operate the platform like a production system: metrics and alerts with runbooks, health/readiness and graceful drain, PITR backups with a rehearsed restore that keeps approvals, identities, inbox/outbox and checkpoints consistent, retention jobs that never discard approved-calculation inputs, and a pilot whose acceptance record completes R1.

## Spec requirements covered
- NFR04 metrics: connector uptime, source lag, backlog, accepted/deduplicated/quarantined counts, cursor/watermark age, latest good sample, stale signals, schema failures, conflicts, replay progress, period completeness, calculation queue age, approval backlog, export failures, outbox age — tagged by tenant/connection without leaking data.
- NFR05 alerts: coverage loss, stuck checkpoint, growing lag, full spool, dead-letter growth, stale open frames, repeated calc failure, overdue accounting; include units/periods, first occurrence, last checkpoint, runbook link; rate-limited; alarms don't assert downtime.
- NFR06 runbooks: PI auth failure, source outage, MQTT reconnect storm, Kafka rebalance/quorum, poison schema, spool pressure, mapping mistakes, late-data repair, stuck recalculation, corrupt counters, approval correction, backup restore.
- NFR07 health/readiness, graceful drain, leases, resource limits; PITR; restore approvals + identities + inbox/outbox + checkpoints together; reconnect with bounded overlap; infra as code; preserve complete immutable inputs for approved calculations through retention.
- §17.1 buffering (24 h, warn 70 %/critical 85 %), retention (Kafka 7 d, samples 90 d, raw 1 y, ledgers/audit 7 y), RPO ≤ 15 min, RTO ≤ 4 h.
- MIG03/MIG06/§19.3/§21.1 release evidence and acceptance.

## Current implementation (verified)
- `health` module (`/api/health` DB check only); console logging; no metrics endpoint; no alerts; Docker Compose with restart policies and healthchecks (frontend/backend/postgres); Prometheus/Grafana/Loki/Promtail containers exist on the host from the instrumental stack (stopped) — reusable.

## Target design
**Observability**: `@willsoto/nestjs-prometheus` (or OpenTelemetry) exposing `/metrics` on API and worker with the NFR04 series (counters/gauges/histograms, labels `tenant_id`, `connection_id`, `job_kind`, `unit_id` where appropriate; no payload data); structured JSON logs with correlation id and redaction (3.11); OpenTelemetry traces optional. Compose `observability` profile: Prometheus, Grafana (dashboards: intake, accounting, workflow, API latency), Loki/Promtail; alert rules in Prometheus/Alertmanager with runbook URL annotations and inhibition/rate limiting.
**Health**: `/health/live` (process), `/health/ready` (DB, Kafka, broker reachability, migrations applied, lease heartbeat for worker); graceful shutdown: API stops accepting, worker finishes in-flight page/run or persists state (ING02); resource limits in Compose/K8s manifests.
**Backups**: Postgres PITR (WAL archiving — `pgbackrest` or managed service); object store snapshots for exports/raw refs; **restore procedure** restores DB (which holds approvals, source identities, inbox/outbox, checkpoints together) and object store to the same point; post-restore: outbox relay republishes pending (consumers dedupe), collectors resume with bounded overlap (PI05), reconciliation report compares approved totals/hashes (T39).
**Retention jobs** (worker): partition drop for `raw_observations` (> 1 y) and `measurement_samples` (> 90 d searchable; archive to object store before drop), Kafka topic retention 7 d, **never** drop rows referenced by `approval_snapshots` inputs — snapshots hold complete input values (WF03/NFR07), verified by a job that checks referential completeness before each drop; legal-hold flag blocks drops per tenant.
**Clock**: NTP check job; source clock skew metric (event_time vs received_at distribution) with alert.
**Runbooks**: `docs/runbooks/*.md` per NFR06 item: symptoms, diagnosis queries/dashboards, safe retry/replay commands (`POST /connections/{id}/replays`, job actions), evidence preservation, validation of recovered totals.
**Pilot & release evidence** (`plans/evidence/release-R1/`): connector-version matrix, fixture results, migration before/after, security summary, UI journey recordings, load-test config/results, restore drill result, alert rehearsal log, training record, signed acceptance (§19.3, MIG06). Pilot per MIG03: one unit/product with PI for ≥ 2 operational weeks incl. month-end, then MQTT/Kafka certification feeds.

## Tests
- **T39 export and restore**: approve + export (hash H) → restore from PITR to a point after approval → replay outbox → downstream receives idempotent duplicate acknowledgement; approved totals and hash unchanged; collectors resume without gaps.
- Alert rehearsal: each NFR05 condition fires exactly one alert with affected units/periods and runbook link; duplicate suppression works; no "downtime" event is created by alarms.
- Readiness: Kafka down → not ready; DB migrations pending → not ready; worker lease stale → not ready.
- Retention: attempt to drop a partition referenced by an approval input → blocked with report; legal hold blocks drop.
- Graceful drain: SIGTERM during a page → page completes or state persisted; no duplicate on restart (reuses 1.5 crash test).
- Metrics: no label or value contains payload/PII (regex scan of `/metrics` output).

## Definition of done
- Dashboards, alerts and runbooks in place and rehearsed; restore drill passed with recorded RPO/RTO; retention safe; pilot completed with acceptance record; R1 definition of done (§21.1) checklist signed in `plans/README.md`.
