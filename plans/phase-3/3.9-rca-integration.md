# 3.9 RCA integration and action feedback

**Status:** 🧪 2026-10-10 (implemented; RCA01–03 fixtures, T42 and the Playwright journey green — awaiting owner review) · **Epic:** P3 E11 · **Spec:** RCA01–RCA03, §16.2 "RCA buttons and priorities", §15.2 `POST /events/{id}/rca-link`, §15.4 `RCARecommended`, D13; the verified RCA save bug (frontend/backend field mismatch) · **Tests:** RCA01–03 fixtures; T42 (advisory never attributes loss) · **Depends on:** 3.1, 1.2, 2.8

## Goal
Keep the RCA module and make its links trustworthy: versioned trigger rules evaluated on confirmed thresholds without duplicate cases, an idempotent event→case link with an evidence package, cases referencing many events/approved losses/work orders, and action tracking whose claimed avoided loss stays distinct from approved historical loss — and fix the RCA save contract that is broken today.

## Spec requirements covered
- RCA01 versioned trigger conditions (repeated functional failure, confirmed duration, quantity, approved impact threshold); open events trigger once threshold exceeded with provisional marker; replays/closure/re-evaluation never duplicate cases.
- RCA02 case references many events, approved losses, work orders; evidence package (source + event revisions, trend window, cause codes, recurrence, approved impact); choose existing or create with authorization; automation creates recommendation or case per policy, never a proven root cause.
- RCA03 actions: owner, due, status, completion evidence, verification window; post-action recurrence vs declared baseline; avoided vs approved vs realized kept distinct; feed learning into reason libraries/strategy requests; AI suggestions attributed and human-accepted.
- §16.2 working create/link action with existing-case search and evidence package.
- T42: IOW/APM advisory with no impact evidence → zero automatic production-loss attribution.

## Current implementation (verified)
- `rca-auto-create.service.ts` runs **only on event create**, first matching rule wins; `rcas.eventId` single link; frontend `buildCreateRcaPayload/buildUpdateRcaPayload` send `teamMembers`, `tenantId`, `organizationId`, `targetCompletionDate` … → backend DTO rejects (400) — **RCA saves from the UI fail** (verified 7 Oct); Plan Dashboard "Create RCA" posts `eventId: 'loss_'+id`; recommendations → tasks via `rcaTaskBridge.ts`; "Push to CMMS" simulated; knowledge base entries only from seeders.

## Target design
**Schema (migration `0019-rca-links`)**
```
rca_case_links: id, tenant_id, rca_id, link_type enum(event, loss_line, work_order, occurrence), target_id, target_revision, linked_by, linked_at, reason, UNIQUE (rca_id, link_type, target_id)
rca_trigger_rules → reuse `rules(kind=rca_trigger_hint)` from 3.8 with thresholds on confirmed values (duration_seconds from closed/elapsed, quantity from accepted loss lines, approved impact from 2.8) and `fireOn enum(threshold_crossed_open, closed, approved)`
rca_trigger_evaluations: id, tenant_id, rule_version_id, occurrence_id|event_id, fired_at, outcome enum(recommended, case_created, suppressed_duplicate), provisional bool, idempotency_key UNIQUE
rca_actions: id, tenant_id, rca_id, title, owner_id, due_date, status, completion_evidence_ref, verification_window_start/end, baseline jsonb {metric, window, value}, post_action jsonb {recurrences, observed_loss}, claimed_avoided_loss numeric null, created_at
```
**Services**
- `RcaTriggerService`: evaluates on `EventChanged` (open events when elapsed crosses threshold → provisional recommendation), on closure (confirmed) and on `PeriodApproved` (approved impact rules); idempotency key = `${ruleVersion}:${occurrenceId}` so replays/re-evaluations are `suppressed_duplicate`; outcome per policy `rca_policy.autoCreate: recommend|create` → `RCARecommended` domain event or case creation with `rca_case_links`. Advisory events never produce loss attribution (T42) — they can only *recommend* a case.
- `RcaLinkService.link(eventId|occurrenceId|lossLineId, rcaId|create)` → idempotent (`UNIQUE`), authorization (reliability_engineer+), builds **evidence package** snapshot: event revisions, source raw refs, trend window spec (signals ± window), cause codes with versions, recurrence (same reason/asset last N months from `kpi_results`), approved impact (loss lines, valuation) → stored on the link.
- `RcaActionService`: CRUD with owner/due/status/evidence; verification evaluation job compares recurrence and observed loss after the action window vs the stored baseline; reports three distinct numbers: claimed avoided (user), approved historical loss (ledger), realized difference (post vs baseline).
- Fix the RCA contract: v2 `POST/PATCH /rcas` DTO matching the frontend model (team members array, dates, scope ids) **or** align the frontend builders to the backend DTO — choose v2 DTO redesign (fields: title, description, status/phase, priority, teamLeadId, teamMemberIds[], targetCloseDate, actualCloseDate, scope) and update `productionApi.ts` builders; include nested evidence/recommendations/logic tree persistence that today is dropped.
- Knowledge base: closing an RCA creates/updates a knowledge entry (closes the gap noted in the application guide); learning → "propose reason code change" request (3.8 reason library) with attribution.

**UI**: RCA module buttons wired: "Create/Link RCA" with existing-case search (by asset, reason, window) and evidence preview; Plan Dashboard period/line → link RCA via loss line; RCA case shows linked events/lines/work orders tabs; actions tab with verification status; recommendation badges from `RCARecommended` events; CMMS push remains a labelled stub (D12).

## Decisions / risks
- D13 defines functional failure taxonomy and thresholds; defaults from current `rca_trigger_configs` migrated as rule version 1.
- **Implemented 2026-10-10 — deviations and open points (engineering defaults, not yet reviewed by the owner):**
  - *Contract changes (flagged; OpenAPI snapshot: 15 operations and 11 schemas added, none changed or removed):* `GET/POST /v2/rcas`, `GET/PATCH /v2/rcas/{id}`, `GET /v2/rcas/{id}/outcome`, `GET/POST /v2/rcas/{id}/links`, `POST /v2/production-events/{id}/rca-link`, `GET /v2/production-events/{id}/rca-evidence`, `GET/POST /v2/rcas/{id}/actions`, `PATCH /v2/rca-actions/{id}`, `POST /v2/rca-actions/{id}/verify`, `GET /v2/rca-recommendations`, `POST /v2/rca-recommendations/{id}/dismiss`. **v1 `/api/rcas` changed (C4 screens):** `eventId`, `description`, `teamLeadId`, `teamMemberIds` optional; `recommendations` / `evidence` / `logicTree` accept JSON text **or** arrays; the tenant of a v1 create comes from the token; v1 updates move `row_version`. The audit interceptor now names `/api/v2/<resource>` writes by resource (was `V2`), so v2 report POSTs are skipped like v1 reports.
  - *Circular FK (1.1 open point) resolved:* the case owns its links (`rca_case_links`, `ON DELETE CASCADE` with the case); `rcas.event_id` and `production_events.rca_id` stay as legacy pointers with `ON DELETE SET NULL`, so deleting either side clears the other's pointer (v1 DELETE of a linked case answers 200; integration-tested). Existing pointers were copied into links (`source = migration`; 3 in the dev DB). Not changed: `rca_evidence`, `rca_recommendations`, `logic_tree_nodes` still reference `rcas` without cascade (v1 child tables), so a v1 case with such children still cannot be deleted.
  - *Trigger rules:* the plan's "defaults from `rca_trigger_configs` migrated as rule version 1" was **not** done — v1 conditions (severity, cost, status) are not facts of the 3.8 grammar and the cost trigger must stay off (D08). Instead the D13 thresholds are the existing `rca_policy` contract (`accounting_policies` kind, seeded approved on first use, unit versions override) and every active `rca_trigger_hint` rule is an extra trigger. For tenants with `v2.rca` on, the v1 auto-create is skipped (one trigger system per plant); flag-off plants keep the v1 trigger configs. Rules carry no `fireOn`: open events fire on elapsed time (provisional), closed events on their confirmed duration; **`approved` / cost triggers on `PeriodApproved` are not implemented** — the only approved-impact trigger the policy defines is `costThreshold`, which is null until the owner sets it.
  - *Trigger semantics:* duration trigger on unplanned downtime only; repeated-failure trigger = D13 functional failures (`failure_events_v`) of the same asset in `repeatWindowDays`, this one included, keyed per occurrence; advisory events never fire policy triggers and a matching hint rule can only recommend (even under `autoCreate: create`). A suppressed duplicate is returned, not stored (the unique key holds one row per firing). A recommendation does **not** change the event's RCA state (no direct write; the 1.2 open point remains for the v1 auto-create path only); linking moves it to `linked` and closing the case to `completed`, both through the event's user layer (`applyUserChangeIn`, row lock), never coding or loss.
  - *Evidence package:* revisions (up to 50) with source revision refs, trend window = signals of the unit ±1 h (ids only, up to 20; no samples copied), cause codes with coding version ids, recurrence = same asset / same reason occurrences in the 90 days before the event (from events, not `kpi_results`, which hold period aggregates without asset / reason), approved impact = active loss lines of the latest approved revision of each period (contribution margin per currency, amount null when any line is unvalued or lacks FX). Manual reconciliation lines without a cause event are not attributed to a case unless linked as a loss line.
  - *Actions:* baseline declared, or counted from history over `windowDays` before the verification window; realized = baseline scaled to the window length − observed; claimed avoided loss per currency (IRR / USD) is the owner's figure; approved historical loss comes from the ledger. Nothing writes to periods, revisions or loss lines (2.8: approved accounting is untouched).
  - *Roles:* case, link and action writes need `reliability_engineer` or `manager_approver` (legacy Engineer / Analyst map to `production_engineer` and cannot write — the owner may want to widen this); reads are any member; unit-limited writers name a unit of their scope (422 INVALID_REFERENCE), tenant-wide cases need a tenant-wide grant (403 TENANT_SCOPE_REQUIRED); foreign path ids 404.
  - *Not built:* "propose reason code change" from learning (3.8 has no change-request mechanism); AI suggestions (none exist); team member editing in the v2 screen (no v2 users endpoint — members persist through the API and the v1 screen; action owner = the current user); the Plan Dashboard v2 "link RCA via loss line" button (loss lines are linked by id from the case's Links tab); `RCARecommended` has no JSON Schema contract yet (it is not an approval message). The v1 Plan Dashboard's `loss_<id>` event id is dropped by the v1 builder (the case is created without event) instead of editing the oversized `PlanDashboard.tsx`.
  - *v1 e2e:* `event-pull-and-rca.spec.ts` — the DTO mismatch is fixed in the backend (array bodies accepted); the `severity: 'Critical'` assertion is retired (no such derivation ever existed; cost trigger off) and replaced by "no severity derived"; the workflow's step 2 checks the event through the API because the fixture event belongs to a fresh "E2E Test Tenant" that the UI's selected plant never lists. `rca-auto-create.spec.ts` cleanup no longer answers 500 (FK fix).
  - *Size rules:* `productionApi.ts` shrinks (RCA code moved to `rca-v1-payload.ts`); `RCAModule.tsx` / `PlanDashboard.tsx` untouched; all new files are under 400 lines.
