# 3.3 Downtime Analysis page

**Status:** 🧪 2026-10-09 (page behind `v2.downtimeAnalysis` in `src/features/downtime-analysis/`, route `/downtime`; AN01 + T24 Playwright green on API-seeded fixtures; additive report parameters / fields (flagged); state timeline from events until 1.10 — see Decisions / risks) · **Epic:** P3 E10/E11 · **Spec:** AN01, KPI05–KPI08 display, DT04 unknown coverage, §16.2 "Downtime Analysis" row, UX03, AN03 grouping · **Tests:** AN01 fixture-driven e2e; T24 · **Depends on:** 3.1, 2.7, 1.10

## Goal
A new page that answers "what is down, why, how often, where, and is it getting better" from server read models only — currently down, KPI summary, reason-hierarchy Pareto with cumulative share, duration/frequency toggle, trends, asset bad actors, crew and calendar comparisons, and a state timeline — with every bar drilling to the same filtered intervals and calculation version.

## Spec requirements covered
- AN01 required views and drill-through with identical server filters and calculation version.
- KPI05–KPI08 labels: planned/unplanned/micro/unknown, stop count vs carry-in, mean completed-stop cohort, scheduled availability vs onstream factor, MTBF with exposure/count, MTTR vs mean downtime to restore.
- DT04 lower-bound known downtime + unknown duration; provisional vs confirmed.
- AN03 site-local grouping; cross-site comparison shows tz/unit/mode/product/policy/coverage.
- UX03 header and states.

## Current implementation (verified)
- No downtime page. Pieces exist in PLA Analytics (Pareto by impact code without cumulative line; trend with unwired selector), Dashboard "top impacted assets" by count, heuristic OEE. No MTBF/MTTR, no timeline, no planned/unplanned, no shift comparison (filter values mismatch).

## Target design
**Route** `/downtime` (nav entry per UX01). `features/downtime/`:
- `DowntimeFilters`: scope (site/units/assets), window presets in plant tz, schedule class (all/planned/unplanned/external/unknown), reason subtree, product, shift, crew; persisted in URL search params (shareable; export uses the same).
- `CurrentlyDownPanel`: `GET /production-events?isOpen=true&physicalTypes=downtime&unitIds…` + `GET /equipment-state-segments?open=true` → unit/asset, state, since, elapsed (server asOf), source quality, provisional flag; actions: code / close (reuse 3.2 dialogs).
- `KpiSummary`: from `GET /reports/downtime` and `GET /reports/reliability` for the filter — total, planned, unplanned, micro-stop, **unknown** (with "known downtime is a lower bound" note when > 0), stop count + carry-in, mean completed-stop duration (cohort label), scheduled availability, onstream factor (denominator label), MTBF (null → "no failures in window, exposure X h"), MTTR or "mean downtime to restore" per label from the API.
- `ReasonPareto`: `groupBy=reasonLevel1` → click → `reasonLevel2` under that parent → … → event list; `metric=duration|frequency` toggle; cumulative % line; bars labelled with `DurationText`.
- `TrendChart`: `groupBy=shift|day|week|month` (site-local), stacked by schedule class; clipped durations (KPI06 note that cohort differs from mean-stop).
- `BadActors`: `groupBy=asset` sorted by duration with frequency secondary; aggregation scope label ("asset totals not additive to unit downtime", ACC06).
- `CrewComparison` / `CalendarComparison`: `groupBy=crew` and side-by-side windows; both show coverage and policy version.
- `StateTimeline`: Gantt of `equipment_state_segments` per unit/asset (lazy-loaded chart; virtualized rows); unknown segments hatched; derived events overlaid; click → event detail drawer.
- Every widget carries `calculationRunIds`/`asOf`/`isProvisional` from its response; `<ScopeHeader>` shows them; export button creates a job with the same filters (2.9).
**Data**: no client aggregation; charts render server numerators/denominators; drill-down passes the same filter object + `runIds` to the event list route (T24).

## Decisions / risks
- Gantt library: build on recharts is awkward; a lightweight custom SVG timeline or `vis-timeline` (adds dependency — ask before adding per standards).
- **Implemented 2026-10-09 — deviations and open points (engineering defaults, not yet reviewed by the owner):**
  - *Backend change (flagged, additive):* `GET /api/v2/reports/downtime` gained `groupBy=reasonChild` + `parentReasonId` (the reason codes one level below a parent; with `reason` / `reasonLevel1` it restricts to the subtree; required with `reasonChild`, refused with other groupings — 422 `PARENT_REASON_REQUIRED` / `PARENT_REASON_NOT_APPLICABLE`; a reason code of another tenant or none — 422 `INVALID_REFERENCE`), and the response gained `groups[].cumulativeShare`, `parentReasonId` and `summary` (the period downtime KPIs of the scope, independent of grouping / class / reason). Still a side-effect-free sum of stored terms in SQL with the 2.7 unit scope. OpenAPI snapshot: 1 parameter and 1 enum value added, no operation added or changed; `schema.d.ts` regenerated; `downtime-drill.int-spec.ts` (6).
  - *Gantt library:* no `vis-timeline` (would be a new dependency); the timeline is plain positioned elements in a lazy chunk.
  - *Asset totals are allocated, not gross:* the plan's fixture expects 60 + 60 min asset bars with a "not additive" label; the 2.7 breakdown (decision "downtime breakdowns") shares overlapping stops equally, so the API gives 45 + 45 min and the asset bars add up to the 90 min unit total. The page shows the server's allocation and says so. A gross per-asset view needs an unallocated breakdown in the KPI run (owner to decide).
  - *Frequency* counts stop occurrences starting in the window (per asset: two overlapping stops of different assets are two occurrences); the drill list shows events overlapping the window. A split stop is one occurrence but several events, and events at the window edge belong to periods that start outside it, so the list count and the bar can differ there (the page says so); the e2e fixture checks equality on whole stops.
  - *1.10 not built:* no `equipment_state_segments` read model — the timeline and "currently down" use production events; "unknown" is stop time with schedule class unknown (the 2.7 deviation), not unknown *state* from stale signals; the DST shift-grouping case (T19 data) is covered by the 2.7 server tests, not by this page's e2e (fixture in UTC).
  - *Filters not offered:* product, shift, crew and a reason-subtree filter for the other widgets — the report endpoints take no such parameter; the reason subtree is the Pareto drill path, crew is a comparison grouping.
  - *Reliability per unit:* the reliability report has no scope total and the browser must not combine units, so MTBF / restore are shown per unit (one row each).
  - *Export:* 2.9 exports only approved `period_summary` / `loss_lines`, so the button exports the approved period summary of the same filters and is disabled while the snapshot is provisional; the e2e fixture is provisional (no approval workflow in the seed), so the export request is covered by the unit test, the page's T24 by network assertions (all report requests share window, units and selector; all responses and the header name the same 3 runs).
  - *Reuse across features:* the page uses the Event Hub environment provider, current-stops panel, event list, drawer and dialogs from `features/event-hub` (no copies). Folder `features/downtime-analysis/` (plan: `features/downtime/`).
  - *Accessibility:* labelled controls, a keyboard-operable bar list beside the (aria-hidden) chart, keyboard-operable timeline bars, tablet viewport (1024 × 768) in the e2e; no axe run (not in A3).
  - *Test data:* each e2e run adds a unit "E2E DT …" with its own published UTC calendar, a product, an approved profile, three periods, two assets, four reason codes and four stops to Demo Plant (plus one unit without a profile from the first seeding attempt).
