# 2.6 Valuation

**Status:** 🧪 implemented 2026-10-09 (backend; finance screens and the "unvalued (policy pending)" UI are Phase 3) · **Epic:** P2 E08 · **Spec:** VAL01–VAL03, §3.3 money as decimals with currency, §14.2 `valuation_rates` (2.2), loss line `valuation snapshot`, D08 · **Tests:** T38 T45 · **Depends on:** 2.2, 2.5

## Goal
Value every loss line with an effective-dated, versioned rate (contribution margin, standard cost or cost per hour) and record a complete valuation snapshot, so financial impact is reproducible, never fabricated (no flat $100/unit), and never double-counted across bases or currencies.

## Spec requirements covered
- VAL01 value by effective-dated product margin or standard cost with currency and unit; GE-style selectable margin versions on profiles; default commercial view = contribution margin; standard cost separately named; neither is realized saving; financial policy approval recorded before production use.
- VAL02 duration cost = `seconds / 3600 × cost_per_hour`; quantity-based and time-based valuations are **alternative** bases for the same loss unless categories are independent cost components; never add lost margin to a downtime rate that includes it.
- VAL03 snapshot rate version, currency, FX version, valuation date, basis, quantity, rounding; never aggregate currencies without approved conversion snapshot; missing price → unvalued quantity, **null cost**; round only presentation totals.

## Current implementation (verified)
- Browser: `Total Loss Value = Σlosses × lossValuePerUnit (100)`, event cost auto-fill (product `standardCost` or impact code rate with duration treated as hours), severity-based `$/h` fallback in `UnifiedAnalyticsService`; `production_events.cost` free input; `impact_codes.cost_per_unit/cost_per_hour/cost_basis` stored; `products.standard_rate` ambiguous. No currency anywhere.

## Target design
**Schema (migration `0014-valuation`)**
```
valuation_policies (accounting_policies kind=valuation_basis): tenant/site scope, default_basis enum(contribution_margin, standard_cost), time_basis_rule enum(exclusive, independent_components), currency char(3), fx_policy enum(none, snapshot), approved_by/at, version
fx_rate_snapshots: id, tenant_id, from_ccy, to_ccy, rate numeric(24,10), as_of, source, version
loss_lines.valuation jsonb -> {basis, rateVersionId, unitValue, currency, fxVersionId|null, valuationDate, quantity|seconds, amount|null, status: valued|unvalued|mixed, roundingPolicy}
loss_line_valuations (normalized copy for querying): id, loss_line_id, basis, rate_version_id, currency, amount numeric(24,8) null, status, valuation_date
```
**Service** `ValuationService.value(run)` (called by 2.5 inside the run):
- For each active loss line: pick rate by `basis` from `valuation_rates` effective at `valuationDate = segment_start` for the slice's profile (quantity bases) or the impact code (cost per hour, time basis); `amount = quantity × unitValue` or `seconds/3600 × costPerHour`; no rate → `amount null`, `status unvalued` (T38).
- **Exclusivity (VAL02)**: a line is valued on one basis per view; reports expose `commercialOpportunity` (margin) and `standardCostView` and `operationalCost` (time) as **separate** totals; the `independent_components` rule allows summing only when policy marks the impact category as an independent cost component.
- Multi-currency (T45): totals grouped by currency; combined total only when `fx_policy=snapshot` and a snapshot exists for the valuation date → `fxVersionId` recorded; otherwise `combinedTotal: null, reason: 'fx_missing'`.
- Rounding: store 8 dp; API returns decimal strings; presentation rounding to currency minor units in the frontend/export layer only.
- Gains and residuals are valued but labelled; never netted into "savings".

**Legacy bridge**: `impact_codes.cost_per_hour/cost_per_unit` migrated into `valuation_rates(impact_code_id, basis=cost_per_hour|standard_cost)` with `state=draft` until finance approves (D08); `products.standard_rate` → `valuation_rates(profile, basis=standard_cost, state=draft)` after owner confirmation (MIG §18.2); the browser `lossValuePerUnit` is removed in 3.5.

**API v2**: valuation appears on `GET /production-periods/{id}` lines and totals; `GET /reports/loss-tree?metric=margin|standard_cost|operational_cost`; `GET/POST /fx-rate-snapshots`; `POST /valuation-policies/{id}/approve`.

## Decisions / risks
- D08 (finance): contribution margin vs standard cost default and joint-product boundary; FX policy. Until approved, the UI shows "unvalued (policy pending)".
- **D08 Q2 answered 2026-10-09: IRR and USD.** Every valued line carries an amount in both reporting currencies; the currency a rate is not entered in is converted through the approved, dated FX table `fx_rates` (instead of `fx_rate_snapshots`: versioned per pair with approval and half-open validity like other master data). No covering approved rate → that amount is null, reason `fx_rate_missing` (never estimated). The XXX placeholder version is kept (v1) and a new v2 lists IRR and USD; v1 is never rewritten and can never value. D08 Q3 (`products.standard_rate`) and Q4 (joint products) stay open.
- **Decision — nothing values before finance approval.** Both seeded versions are unapproved; `POST /valuation-policies/{id}/approve` (manager approver, tenant-wide grant, author ≠ approver per the policies README) is the VAL01 sign-off. Until then every line is `unvalued` / `policy_unapproved` and the run still records the policy version. Valuation applies the highest **approved** version in force (a newer draft never blocks an approved one). New tenants get one unapproved IRR / USD version on first use.
- **Decision — valuation inside the run, reproducible.** The run freezes the policy body and every approved rate / FX version it may use, **with their values** (`calculation_runs.valuation_context`), and hashes it. A rate, FX or policy approval therefore changes the input hash: drafts revalue on their next recompute, in-review revisions become stale, approved revisions get a change proposal (never an overwrite). Approvals do not queue recalculations by themselves (as with 2.2 rates): next recompute, `POST /production-periods/recalculate` or the sweep. Engine version `+val.2.6.0` → each draft gets a new run on its next recompute; approved revisions from before 2.6 stay unvalued (reason "calculated before valuation") until revised.
- **Decision — views, kinds and units.** Views are never added (VAL02); `independent_components` is a separately named totals view, only for impact codes the policy lists. Kinds are never netted: gains (negative) and residuals are valued in their own rows; the period / export "loss value" sums availability, performance, quality, unaccounted-classified and bridge lines. Quantity rates must be per the line's unit (`uom_mismatch` otherwise, never converted); cost per hour applies to availability lines with a cause (lost seconds = interval × the cause's share). Time-uniform lines (availability, schedule exclusion, time cost) are split at rate-version edges (10:00–10:30 v1, 10:30–11:00 v2); performance / quality lines use the rate in force at the valuation date (segment start). A gap in the rate history leaves the whole line unvalued (no partial value).
- **Decision — totals.** Missing price → line unvalued with its quantity kept (`unvaluedQuantity`); the currency total sums the valued lines with status `mixed` (null when nothing is valued) (T38). A missing FX rate makes that currency's total null (`fx_rate_missing`) while `nativeAmount` keeps the per-currency sum (T45). Stored with 8 dp; API decimal strings are canonical (no trailing zeros, the v2 convention) rather than `"1234.56780000"`; exports round half-even to 2 decimals per row, totals computed from unrounded values.
- **Decision — 2.8 manual lines.** Reconciliation lines have no interval: they are valued at the slice start from the run's frozen context (no time-cost view); decided candidates scale their run valuation by decided / proposed quantity (rejected / replaced → 0). The valuation enters the reviewed content and its hash only for runs with a valuation context, so the content hashes of pre-2.6 revisions do not change.
- **Contract change (flagged) — `PeriodApproved` / `PeriodRestated` v1 widened additively:** `valuation.status` `unvalued | valued | mixed`, `reason` nullable, optional `policyVersion`, `defaultView`, `currencies` and `totals[]` (slice, view, currency, amount decimal or null, status, reasons, unvalued quantity); `currency` stays null (each total names its currency). Every payload valid before stays valid; `schemaVersion` stays 1.
- **Contract change (flagged) — export columns:** `value, currency, valuation_status, valuation_reason` become `valuation_view, value_1, currency_1, value_2, currency_2, valuation_status, valuation_reason` (both reporting currencies of the snapshot's policy, default view); snapshots approved before 2.6 render unvalued with the reason.
- **Contract change (flagged) — API:** `GET /production-periods/{id}/accounting` adds `lines[].valuation` and `valuationTotals`; its `policyVersion` now also names `valuation_basis@n`. Additive.
- **Deviation — legacy costs not migrated.** `impact_codes.cost_per_hour / cost_per_unit` have no currency (v1 never stored one; the browser only printed "$") and `valuation_rates.currency` is required, so draft rates would guess the currency (MIG §18.2). The values stay on `impact_codes` for finance to re-enter as IRR or USD rates; `products.standard_rate` stays unused until D08 Q3. The browser `lossValuePerUnit` goes in 3.5.
- **Deviation — RCA cost trigger stays off** until 3.9: `rca_policy.costThreshold` is null (no amount was given) and the trigger service is 3.9; the v1 `rca-trigger-evaluator` (legacy `production_events.cost`) is unchanged.
- **Deviation — no `ValuationService` class / `valuation_policies` table:** the policy is `accounting_policies` kind `valuation_basis` (0.2 design); valuation is pure domain code called by the run.
- **Not done here:** finance UI and the "unvalued (policy pending)" banners (3.5 / 3.6); cost tiles on dashboards (3.3 / 3.6 read `/reports/loss-value`); automatic recalculation on rate / FX / policy approval.
