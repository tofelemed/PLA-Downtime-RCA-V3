# 2.2 Production profiles and rates

**Status:** 🧪 implemented 2026-10-09 (backend; profiles UI is 3.4) · **Epic:** P2 E07 · **Spec:** PLAN01, PLAN06, §3.1 capacity vocabulary, VAL01 (margin versions live on profiles), §14.2 `production_profiles`, `unit_product_rates`, `valuation_rates`, MIG §18.2 "ambiguous standard_rate", D05 D08 · **Tests:** rate-version fixtures feeding T30/T28 · **Depends on:** 0.4, 1.3

## Goal
Model what a unit can produce: per unit × product × operating mode, the quantity unit, sustained capacity (MSC/MPC), planning rate, budget and forecast as separate effective-dated, approved versions, plus measurement, OEE and valuation policies. These feed plan generation (2.3), loss derivation (2.5), OEE (2.7) and valuation (2.6).

## Spec requirements covered
- PLAN01 profiles hold sustained and planning rates, quantity unit, rate timebase, operating mode, product mix constraints, measurement policy, OEE policy, valuation policy; rates/margins effective-dated with approval versions, **no overlapping active versions** per key; sustained capacity for capacity analysis, approved planning baseline for plan analysis.
- §3.1: nameplate, demonstrated, MSC/MPC, budget, forecast and approved plan are separate values — "do not rename all of them as target".
- PLAN06 monthly budget and daily forecast import/entry as separate versions; MPC history and forecast overrides visible; validate interval consistency, govern historical corrections through revisions (not S3's older-date restriction).
- VAL01 GE-style selectable margin versions preserved on profiles.
- §18.2: `standard_rate` ambiguous → separate rate and cost after owner confirmation; no blind rename.

## Current implementation (verified)
- `units.capacity`, `units.unit_of_measure`, `units.ideal_cycle_time` — stored, never read. `products.standard_rate` (property `standardCost`) used only by the browser cost auto-fill. No unit × product pairing, no effective dating, no approvals. Template default assumes 100 units/h.

## Target design
**Schema (migration `0010-profiles-rates`)**
```
production_profiles: id, tenant_id, unit_id, product_id, operating_mode varchar default 'normal', quantity_uom, rate_timebase enum(s,min,h,d),
  capacity_model enum(single_stream, shared_capacity, independent_streams), actuals_policy_id (→ source_authority_policies 1.10), oee_policy_id, valuation_policy_id,
  product_mix_constraints jsonb null, effective_from, effective_to, version, state enum(draft, approved, retired), approved_by/at
  UNIQUE (tenant_id, unit_id, product_id, operating_mode, version); EXCLUDE overlapping approved versions per (unit, product, mode)
unit_product_rates: id, tenant_id, profile_id, rate_kind enum(nameplate, demonstrated, sustained, planning, budget, forecast), rate numeric(24,8), timebase enum(s,min,h,d),
  effective_from, effective_to, version, state enum(draft, approved, retired), approved_by/at, source enum(manual, import), external_id null
  EXCLUDE USING gist (profile_id WITH =, rate_kind WITH =, tstzrange(effective_from, effective_to,'[)') WITH &&) WHERE (state='approved')
valuation_rates: id, tenant_id, profile_id null, impact_code_id null, basis enum(contribution_margin, standard_cost, cost_per_hour), value numeric(24,8), currency char(3), per_uom, effective_from/to, version, state, approved_by/at
  CHECK (profile_id IS NOT NULL) <> (impact_code_id IS NOT NULL)
rate_imports: id, tenant_id, kind enum(budget, forecast, mpc), external_id, revision, file_ref, state, counts, imported_by
```
**Services**
- `ProfileService.resolve(unitId, productId, mode, at)` → approved profile + rates per kind effective at `at`; `ratePerSecond(rate, timebase)`; `idealProductionSeconds(qty, at)` = qty / sustainedRatePerSecond (KPI01 input).
- `RateService.approve(rateId)` enforces no-overlap for approved kind; `supersede` closes previous `effective_to` at new `effective_from` (historical corrections create new versions, never edit approved rows).
- Budget/forecast import (CSV/JSON) → `rate_imports` + `unit_product_rates(kind=budget|forecast, source=import, external_id)`; revisions are corrections, not additions.
- Legacy bridge: seed one `production_profiles` row per existing (unit, product) seen in plans; `sustained` rate from `units.capacity/unit_of_measure` if present; `planning` left empty (plans then require explicit rate); `products.standard_rate` migrated to `valuation_rates(basis=standard_cost)` **only** after D08 confirmation — until then shown as "unconfirmed legacy cost".

**API v2** (§15.2 `/profiles`, master data conventions): `GET/POST /profiles`, `POST /profiles/{id}/approve|retire`, `GET/POST /profiles/{id}/rates`, `POST /rates/{id}/approve`, `GET /profiles/resolve?unitId&productId&at`, `POST /rate-imports` (202 job), `GET/POST /valuation-rates`.

## Decisions / risks
- **Deviation — legacy sustained rate not seeded.** v1 `units.capacity` has no timebase (and the template's "100/h" is a UI default), so turning it into a `sustained` rate would guess the timebase (MIG §18.2). It is kept as a review value on the draft profile; an engineer enters and approves the sustained rate. Seeded profiles are drafts (nobody approved them), without `rate_timebase`; approval needs `quantityUom` + `rateTimebase` (422 `PROFILE_INCOMPLETE`).
- **Deviation — policy references not writable yet.** `actuals_policy_id` / `oee_policy_id` / `valuation_policy_id` exist as nullable columns but are not accepted by the API: there is no policy table to check them against (1.10 and the policy store), and unchecked foreign ids are not accepted anywhere in v2.
- Added beyond the plan's API list: `PATCH /profiles/{id}` (drafts, If-Match — needed to complete seeded drafts), `GET /rates/{id}`, rate / valuation-rate retire, valuation-rate approve, `GET /rate-imports/{id}` (the 202 status URL).
- Imports write **approved** rows (the test "revision → previous retired, not a second active row" needs active imported rows); importing therefore needs the approver role. Rate rows of a document are identified by the document's `external_id`; a revision replaces the whole document.
- Approval does not enforce submitter ≠ approver (D06 governs accounting revisions); logged as an engineering default.
- `numeric` columns are parsed to JS numbers by `registerPgTypeParsers` (app/worker); values beyond ~15 significant digits would lose precision on read. Views normalise to canonical decimal strings.
- D05/D08 confirmations needed before legacy cost/rate reuse; until then plan generation requires explicit planning rates (no 100/h default).
- `shared_capacity`/`independent_streams` models are stored now and used by 2.3 only behind the `CONCURRENT_PRODUCTS` flag (D14).
