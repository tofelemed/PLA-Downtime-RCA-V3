# 2.4 Production periods and actuals results

**Status:** 🧪 implemented 2026-10-09 (backend; periods UI is Phase 3; accounting revisions and restatement proposals are 2.8) · **Epic:** P2 E08 · **Spec:** ACT01–ACT08, §3.1 reporting grain, §14.2 `production_periods`, `period_product_slices`, `actuals_results`, `external_production_reports`, SRC01 (consumer), D05 · **Tests:** T25 T26 T27 (persisted), T12, T44 · **Depends on:** 2.1, 2.3, 1.7, 1.10

## Goal
Create the accounting grain — one production period per unit per calendar leaf with product slices — and compute authoritative actuals (gross, good, rejects, rework) per slice from the selected source with coverage and quality, plus governed manual adjustments and the external daily-production (Maximo) record, keeping actuals revisions separate from loss-explanation revisions.

## Spec requirements covered
- ACT01 slice records gross/good/reject/rework, method, source segments, coverage, quality, revision; good = accepted at accounting boundary; inventory movements are not production without a mass-balance policy.
- ACT02 output events counted once; spanning events need measured distribution or approved proportional estimate marked Estimated; counter deltas with splits; no negative delta.
- ACT03/ACT04 engine rules (implemented in 1.7) applied per period with persisted method and excluded bad intervals.
- ACT05 `coverageRatio`, `measuredQuantity`, `estimatedQuantity`, quality flags; missing = null not zero; approval needs 100 % accepted coverage (approved substitutions count, estimated share exposed) unless a versioned policy says otherwise.
- ACT06 manual actuals/corrections need reason, evidence, unit, author, window, independent approval when affecting approved reports; raw immutable; daily-production revision ≠ PLA explanation revision (T44).
- ACT07 rejects once; rework → good only when accepted and not double counted; gross vs good basis declared; never invent 100 % quality.
- ACT08 external daily-production record (externalReportId, revision, site, local date, tz, UTC boundaries, lines, basis, status, approvedAt, evidence); status mapping to certified eligibility; dedupe by report id + revision; later revision = correction candidate.
- §3.1 never count both shift and daily rows; campaigns split periods; concurrent products = separate slices with explicit shared-capacity model.

## Current implementation (verified)
- `production_losses.actual` typed by user or synced from Σ ProductionOutput event quantities on a button; `oee_summaries` time columns not writable; no period entity; no coverage; no external report import; `reconcile_forms`/plans mix actuals and explanations.

## Target design
**Schema (migration `0012-periods-actuals`)**
```
production_periods: id, tenant_id, unit_id, shift_instance_id, utc_start, utc_end, local_date, shift_name, selected_plan_version_id null, state_readiness enum(open, complete_inputs, reconciled) (display only; workflow lives in accounting_revisions)
  UNIQUE (tenant_id, unit_id, utc_start)
period_product_slices: id, period_id, product_id, profile_id, plan_period_id null, campaign_from/to null, actuals_policy_id, UNIQUE (period_id, product_id, campaign_from)
actuals_results: id, tenant_id, calculation_run_id (2.5) | actuals_run_id, slice_id, gross numeric(24,8) null, good null, reject null, rework_accepted null, uom,
  method enum(output_events, counter_delta, rate_integration, manual, external_report, mixed), coverage_ratio numeric(9,8), measured_qty, estimated_qty, quality_state enum(complete, partial, missing, conflict),
  source_segments jsonb [{signalId|source, from, to, qty, method, quality}], exceptions jsonb, computed_at
actuals_adjustments: id, tenant_id, slice_id, kind enum(gross, good, reject, rework), quantity, uom, basis, reason, evidence_ref, measurement_window, author_id, state enum(proposed, approved, rejected), approved_by/at (≠ author)
external_production_reports: id, tenant_id, connection_id null, external_report_id, external_revision, site_id, local_production_date, timezone, utc_start, utc_end, lines jsonb [{unitId, productId, gross|good|reject, uom}], basis enum(gross, good), source_status, certified_eligible bool, approved_at_source, evidence_ref, imported_at
  UNIQUE (tenant_id, external_report_id, external_revision)
```
**Period lifecycle (worker)**
- `PeriodMaterializer`: at each shift end (and on demand/backfill) create `production_periods` from `shift_instances` for units with an approved profile; slices from the accounting-baseline plan version's `plan_periods` (campaign-aware) or from the profile's default product when no plan.
- `ActualsRunner.run(periodId)`: for each slice resolve authority (1.10) → `method`; compute via 1.7 engine within `[utc_start, utc_end)`:
  - `output_events`: Σ `production_output` events with timestamp in window, once per source identity; spanning events: measured distribution from attributes if present, else proportional-time estimate marked `estimated` (policy `coverage_gate.allowProportionalEstimate`).
  - `counter_delta` / `rate_integration`: engine result incl. exceptions → `quality_state`.
  - `external_report`: if policy says certified external record is authority, take line quantities when `certified_eligible`.
  - rejects/rework per ACT07; `good = gross − reject + rework_accepted` when basis gross; if only good known → `gross null`, quality factor unavailable (never 100 %).
  - approved `actuals_adjustments` applied as separate component with `estimated` share.
  - coverage = observed/accepted seconds ÷ window; `quality_state` from exceptions; result immutable per run.
- Triggers: `Normalized` samples/events in window, authority change, adjustment approval, external report import → `PeriodRecalculateRequested` (consumed by 2.5 which calls `ActualsRunner` inside its run so actuals and losses share one run).
- **Separation (ACT06/T44)**: actuals changes create a new *actuals* result in a new run; loss-explanation changes (2.8 draft lines) reuse the current actuals result without recomputing it unless inputs changed; both referenced by the accounting revision.

**API v2**: `GET /production-periods?unitIds&productIds&from&to&readiness&workflowState` (grid with authoritative summaries), `GET /production-periods/{id}` (slices, actuals with provenance), `POST /actuals/adjustments`, `POST /actuals/adjustments/{id}/approve|reject`, `POST /external-production-reports` (import; 202 job for files), `POST /production-periods/{id}/recompute` (202).

## Decisions / risks
- D05 decides authority and gross/good boundary per product; defaults: output EFs primary, counters fallback, basis gross.
- D03 daily-leaf sites: periods are daily; `shift_name` null.
- Mass-balance from tank levels is explicitly out unless a policy exists (ACT01) — not planned for R1.
- **Deviation — source authority without 1.10.** `source_authority_policies`, `source_segments` and `AuthorityService` (1.10) do not exist; the runner applies the versioned `source_authority` policy itself per slice and period (primary / fallback conditions / conflict tolerance), records the choice (`fallback_used`, `source_conflict`) in the result and persists no source segments. 1.10 replaces `selectAuthority` with segment-level authority. `primary_stale` is treated like `primary_missing` (no staleness model yet).
- **Deviation — policy store introduced here.** The 0.2 design's `accounting_policies` table is created by this migration for the two kinds 2.4 consumes; there is no policy API yet (versions are seeded or written by SQL; management comes with 2.5 / 2.8). A unit-scoped version wins over the tenant-wide one; `productId` in a policy body is not resolved yet (all products of the scope). `contracts/policies/source_authority.schema.json` gains the source `external_report`.
- **Deviation — schema additions:** periods carry `is_excluded`, `exclusion_kind`, `calendar_version_id`, `current_actuals_run_id`, `slices_resolved_at`, `warnings`; slices carry `source`, `window_from/to`, `quantity_uom`, `superseded_at` (the target's UNIQUE (period, product, campaign_from) is UNIQUE (period, product, window_from) among active slices); results carry `period_id`, `basis`, `coverage` (seconds) and `adjustment_ids`; `actuals_runs` stands in for `calculation_run_id` until 2.5; adjustments carry `period_id`, `unit_id`, `decision_reason` and a basis of measured / estimated; reports carry `state`, `superseded_by_id`, `imported_by`. `state_readiness` never becomes `reconciled` in 2.4 (2.8).
- **Deviation — routes:** added `POST /production-periods/materialize`, `GET /actuals/adjustments/{id}`, `POST /external-production-reports/import` (CSV, 202), `GET /external-production-reports/{id}`, `GET /actuals-jobs/{id}`; the grid's `workflowState` filter waits for 2.8 (only `readiness` now).
- **Deviation — measured distribution:** no source delivers a per-period distribution of an output frame yet (D02 item 3); the engine accepts one (`distribution`), the loader passes none, so spanning frames are estimated or flagged.
- **Decision — output event quantity is gross.** As in 1.7, an output event's `quantity` is gross and `defective_quantity` its rejects (good = gross − rejects). The default PI attribute rule maps `GoodQty` to `quantity`; if D02 item 3 shows that attribute is net of scrap, the mapping (not the engine) changes.
- **Decision — external records only at their own grain.** A certified record is used only for a period whose UTC bounds equal the record's (daily-leaf units); on shift-leaf units it is an `external_report_grain_mismatch` finding and is never pro-rated (§3.1). A later revision supersedes the current one even when its status is not certified (it is the newer statement; the period is then `missing` until a certified revision arrives).
- **Decision — coverage of output events** is the union of the booked event intervals inside the period, so idle time between frames lowers coverage (and blocks approval in 2.8 under the 100 % gate) until covered by an approved substitution or a policy version with a lower `requiredCoverageRatio`.
- **Restatement:** `PlanVersionApproved` re-resolves slices of open periods only; reconciled periods (2.8) are logged for the `period_change_proposals` of 2.8 and never re-sliced.
- **Not done here:** the 2.5 calculation-run container (2.5); accounting revisions and the revision half of T44 (2.8); rebinding the v1 Plan Dashboard to `production_losses_v` (Phase 3 — the view exists with the v1 column names); periods UI (Phase 3).
