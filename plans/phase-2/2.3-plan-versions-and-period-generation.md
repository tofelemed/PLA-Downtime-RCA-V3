# 2.3 Plan versions and period generation

**Status:** ⬜ not started · **Epic:** P2 E07 · **Spec:** PLAN02–PLAN05, §14.2 `production_plans`, `plan_versions`, `plan_periods`, §15.2 plan routes, D14 · **Tests:** T43; exact target distribution fixtures · **Depends on:** 2.1, 2.2

## Goal
Keep the existing plan header and forms, but make a plan a **versioned** object whose approved version generates concrete per-shift/day **plan periods** per product slice with exact target distribution from schedules and rates — the baseline the plan ledger reconciles against.

## Spec requirements covered
- PLAN02 retain header (name, unit, dates, recurrence, template); add plan version, product slices, basis, schedule version, target source, approval state; time-based plans from schedules × rates; quantity-based targets distributed by explicit weights; sequential campaigns; concurrent products; **default distribution proportional to scheduled planning capacity, not 100/h**.
- PLAN03 preview before approval; each leaf period has UTC start/end, local date, shift, slice, target, sustained capacity, source versions; slice targets sum exactly to header target with deterministic rounding remainder to last eligible slice; no positive target on a schedule with no eligible time.
- PLAN04 at most one approved version per unit/product/overlapping interval within a scenario; scenarios allowed, one is accounting baseline; post-approval changes → new version + restatement proposal; forecast changes don't alter approved plan.
- PLAN05 concurrent products need independent streams or joint recipe; sequential campaigns non-overlapping; unlike quantities not totaled.

## Current implementation (verified)
- `production_plans`: one `target_quantity` for `[start_date, end_date]`, `useful_production_time` JSON (browser-only), `recurrence`, `data_entry_frequency`, approval columns set by client strings; `unit_id/product_id` varchar without FK. Template default `plannedQuantity = hours × 100`. No periods, no versions, no overlap check.

## Target design
**Schema (migration `0011-plan-versions`)**
```
production_plans: + legacy_id (=id), scenario_id FK (default scenario per tenant), current_version int, unit_id/product_id → uuid FKs (expand/contract)
plan_scenarios: id, tenant_id, name, is_accounting_baseline bool (exactly one true per tenant/site)
plan_versions: id, tenant_id, plan_id, version, basis enum(time, quantity, manual), calendar_version_id, header_target numeric(24,8) null, target_source enum(generated, entered, imported),
  distribution enum(scheduled_capacity, explicit_weights, equal), approval_state enum(draft, submitted, approved, superseded), approved_by/at, supersedes_version_id, change_reason
plan_product_slices: id, plan_version_id, product_id, profile_id, campaign_from, campaign_to (null = whole plan), weight numeric(12,8) null, stream enum(sequential, independent, shared)
plan_periods: id, tenant_id, plan_version_id, slice_id, unit_id, shift_instance_id, utc_start, utc_end, local_date, shift_name, target numeric(24,8), sustained_capacity_qty numeric(24,8), planning_rate_version_id, sustained_rate_version_id, is_excluded
  UNIQUE (plan_version_id, slice_id, utc_start)
EXCLUDE (approved) overlapping (scenario, unit, product, tstzrange(start,end)) across plan_versions  -- PLAN04, enforced in service + deferred check
```
**Generation** `PlanPeriodGenerator.generate(planVersion, preview)`:
1. Leaf windows = `shift_instances` of the unit's published calendar within `[start_date, end_date)` (daily leaves if site policy = daily).
2. Per slice and leaf: `scheduledSeconds` (excluded instances → 0), `planningCapacity = scheduledSeconds × planningRatePerSecond(at)`, `sustainedCapacity = scheduledSeconds × sustainedRatePerSecond`.
3. `basis=time`: `target = planningCapacity`; header target = Σ.
   `basis=quantity`: distribute header target by `distribution`: `scheduled_capacity` → proportional to `planningCapacity` (default); `explicit_weights` → slice/leaf weights; `equal` → eligible leaves only. Decimal arithmetic (8 dp), **remainder assigned to the last eligible leaf** so Σ = header exactly; zero eligible time with positive target → 422 `NO_ELIGIBLE_TIME` (PLAN03).
   `basis=manual`: imported/entered per-leaf targets, validated Σ = header.
4. Sequential campaigns: slices with non-overlapping campaign ranges — leaves assigned to the slice whose campaign covers them (422 on overlap). Concurrent (`CONCURRENT_PRODUCTS` flag): `independent` streams generate per-slice targets with separate capacity; `shared` requires a joint recipe (`profile.product_mix_constraints`) defining feasible rates — infeasible → 422 (T43).
5. `preview=true` returns periods + warnings (DST, exclusions, missing rates) without persisting.

**Approval** `PlanVersionService.approve(versionId, expectedVersion, reason)`: validates no overlapping approved version in the scenario (PLAN04), freezes periods, marks previous version `superseded`; if any `production_periods` already approved use the old version → create `period_change_proposals` (2.8) instead of silently rebaselining.

**Legacy bridge**: v1 `PUT /production-plans/{id}` creates/updates the **draft** version; `plannedQuantity` maps to `header_target` with `basis=quantity`, `distribution=scheduled_capacity`; v1 approval fields map to `approval_state` through the same service (no more client strings).

**API v2** (§15.2): `GET/POST /production-plans` (header + draft version), `POST /production-plans/{id}/generate-periods {version, distribution, preview}`, `POST /production-plans/{id}/approve {expectedVersion, reason}`, `GET /production-plans/{id}/versions/{v}/periods`, `GET/POST /plan-scenarios`.

## Tests
- Distribution: header 1000 over leaves with planning capacities [300, 300, 400] → [300, 300, 400]; with capacities producing repeating decimals → Σ exactly 1000.00000000, remainder on last eligible leaf; excluded leaf gets 0.
- Time basis: 8 h × 90 t/h with 1 h excluded → 630 t (T28 input).
- No eligible time + positive target → 422.
- PLAN04: approving overlapping version in same scenario → 409; different scenario allowed; baseline flag unique.
- **T43 concurrent products**: shared-capacity recipe with two slices; infeasible combined rate → 422; feasible → separate slice targets; unlike UoM not summed in response totals.
- Approving a version while periods already approved → change proposal created, original targets unchanged.
- Legacy: v1 update of `plannedQuantity` regenerates draft periods; approved version untouched.

## Definition of done
- Plans versioned; periods generated with exact sums and previews; approval exclusive per scenario; legacy header still editable via v1; T43 and distribution fixtures green.

## Decisions / risks
- D14 (concurrent products) default: sequential campaigns only in R1; concurrent behind flag.
- Daily-leaf sites: generator uses daily instances when `calendar_versions.shift_templates` is a single 24 h template (D03).
