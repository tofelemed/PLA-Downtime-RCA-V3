# 2.1 Calendars and shift instances

**Status:** 🧪 implemented 2026-10-09 (backend; calendar UI is 3.4) · **Epic:** P2 E07 · **Spec:** CAL01, CAL02, §3.3 timezones, §14.2 `calendar_versions`, `shift_instances`, D03 · **Tests:** T19 T29 · **Depends on:** 0.4

## Goal
Give every tenant/site/unit a versioned calendar — IANA timezone, operational day start, shift templates, working intervals, holidays and exclusions — and generate concrete, non-overlapping shift instances with stored UTC boundaries so periods, downtime clipping and OEE denominators use plant-local time correctly, including DST.

## Spec requirements covered
- CAL01 site calendars (timezone, operational day start, shift templates, working intervals, holidays, exceptional exclusions); unit calendars inherit with effective-dated overrides; shifts may cross midnight; production date by operational-day rule; **store generated UTC boundaries and local labels** so later tz-library changes don't reinterpret approved periods.
- CAL02 DST: fall-back repeated hour represented twice with distinct offsets; spring-forward missing hour contributes no time; 23/25-hour days not forced to 24; crews are independent rotations and never alter the denominator.
- §3.3 render plant-local time with zone and offset.

## Current implementation (verified)
- `tenants.timezone varchar(100)` editable in UI, **never read** by backend. Shifts/crews are free text on events and plans (`shift`, `crew`). Plans hold `useful_production_time` JSON (`{Monday:{start,end}}`) interpreted only in the browser. Buckets in reporting are UTC days. No holidays/exclusions.

## Target design
**Schema (migration `0009-calendars`)**
```
sites: id, tenant_id, organization_id, name, timezone (IANA), operational_day_start time, is_default   -- tenant = plant today; site table introduced for §3.1 hierarchy; default one site per tenant
units: + site_id FK (backfill to default site)
calendar_versions: id, tenant_id, site_id, unit_id null (override), version, state enum(draft, published), timezone, operational_day_start,
  shift_templates jsonb [{name, startLocal "06:00", endLocal "14:00", daysOfWeek[]}], working_intervals jsonb (optional finer than shifts),
  holidays jsonb [{date, name, treatment: excluded|reduced}], exclusions jsonb [{from, to, reason, kind: planned_shutdown|turnaround|no_demand}],
  effective_from, effective_to, published_by/at
  -- published rows immutable; new changes = new version
shift_instances: id, tenant_id, calendar_version_id, unit_id, local_date date, shift_name, utc_start, utc_end, utc_offset_start int, utc_offset_end int, is_excluded bool, exclusion_reason, crew_id null
  UNIQUE (unit_id, utc_start); EXCLUDE (unit_id, tstzrange(utc_start, utc_end,'[)') &&)
crews: id, tenant_id, site_id, name ; crew_rotations: id, crew_id, pattern jsonb, effective_from/to  (assignment only)
```
**Generator** `CalendarService.generate(calendarVersion, localDateRange)` (luxon with IANA zones): for each local date and shift template compute `utc_start/utc_end` via zone conversion; crossing midnight → `utc_end` on next local date; production date = date of operational-day start containing the shift start; DST: use luxon's explicit offset resolution — fall-back ambiguous local time generates two instances with offsets (`utc_offset_start` differs) when a shift boundary falls in the repeated hour, spring-forward gap skipped (shift shortened by 1 h); exclusions mark instances `is_excluded` (whole or split instance). Idempotent: regenerating a published version for a range yields identical rows (hash compared).

**Scheduled time** `CalendarService.scheduledSeconds(unitId, window)` = Σ over `shift_instances` ∩ window where `is_excluded=false` (half-open) → S for KPI01; `exclusions` → "schedule exclusion" bucket for the capacity ledger (ACC01).

**Boundaries** `CalendarService.boundaries(unitId, window)` → sorted UTC instants of shift/day changes for DT05 splitting (used by 1.1 `splitAt`).

**API v2** (§15.2): `GET/POST /calendar-versions`, `POST /calendar-versions/{id}/publish`, `POST /calendars/preview {unitId, localFrom, localTo, candidateVersion}` → instances + DST warnings, `GET /shift-instances?unitId&from&to`, `GET/POST /crews`, `/crew-rotations`.

## Tests
- **T19 DST calendar**: daily 3-shift template on fall-back and spring-forward days → 25 h and 23 h total scheduled seconds; repeated hour produces two instances/offsets; no 24 h forcing; quantities per instance unaffected by crew changes.
- **T29 cross-shift clipping** (with 1.1): stop 05:50–06:20 local around 06:00 boundary → 600 s prior shift, 1200 s next; one occurrence.
- Midnight-crossing shift (22:00–06:00) gets production date of its start's operational day.
- Exclusion inside a shift splits the instance; `scheduledSeconds` excludes it; capacity ledger sees `schedule_exclusion`.
- Published version immutable (PATCH → 409); preview of candidate shows diff vs current.
- Regeneration idempotent.

## Definition of done
- Calendars versioned and published; shift instances stored in UTC with offsets; scheduled seconds and boundaries available to downtime/accounting; v1 shift labels derived; T19 T29 green.

## Decisions / risks
- D03 confirms shift templates/day start; defaults (06:00 start, 3 × 8 h) are seed configuration.
- Introducing `sites` adds a hierarchy level the UI doesn't show yet; one default site per tenant keeps v1 working.

- **Deviations / decisions (9 Oct 2026):**
  - **Repeated hour:** "two instances" happens when a shift *boundary* falls inside the fall-back hour (the wall-time preimage is two disjoint UTC pieces, e.g. Berlin 02:30–10:30 on 25 Oct = 00:30–01:00Z at +02:00 and 01:30–09:30Z at +01:00). A shift that contains the whole repeated hour (the D03 22:00–06:00 night) stays one 9 h instance with `utc_offset_start` 120 and `utc_offset_end` 60. A boundary inside a spring-forward gap moves to the end of the gap.
  - **Offsets** are stored in minutes east of UTC; `utc_offset_end` is the offset in force just before the end. Local labels `local_start` / `local_end` (ISO 8601 with offset) are stored as CAL01 asks: two columns not in the §14.2 sketch.
  - **Exclusion kind:** `shift_instances.exclusion_kind` (`holiday`, `planned_shutdown`, `turnaround`, `no_demand`, `non_working`) added next to `exclusion_reason` so the capacity ledger can bucket `schedule_exclusion` per kind. Exclusion instants must carry an offset.
  - **Holidays:** `excluded` removes every shift of that operational date from scheduled time (D03); `reduced` keeps the shifts and only warns in the preview (no reduction rule is defined yet; follow-up with operations).
  - **Working intervals:** when a version has any, shift time outside them is excluded as `non_working`.
  - **Effective dates** are operational dates, `effective_to` exclusive; the highest published version in force wins (unit override before site calendar); a published row is never edited to close it.
  - **Publish window:** past dates only gap-filled (≤ 366 days back), future dates (from tomorrow) regenerated, horizon 90 days; publication and generation are one transaction. A new crew rotation regenerates tomorrow … +89 d of the crew's site (only `crew_id` can differ); crews never change bounds or scheduled seconds (T19).
  - **Day changes** for `boundaries()` are the shift starts/ends (3 × 8 h covers the 06:00 day start); a calendar with gaps gets no extra day-start cut.
  - **v1 label:** derived only where an instance covers the event start; otherwise the stored free text is still returned.
  - **No calendar seeded:** the D03 Asia/Tehran 3 × 8 h calendar is configuration the plant creates through the API (or the 3.4 UI); the migration creates only default sites (the HDPE tenant's zone comes from `tenants.timezone`, else UTC flagged). No demo seeder was added.
  - **Not done here:** frontend calendar editor (3.4); KPI/accounting consumers of `scheduledSeconds` (2.4 / 2.5 / 2.7); sites create/update (list/get only); outbox domain events for publication (none listed in the plan).
