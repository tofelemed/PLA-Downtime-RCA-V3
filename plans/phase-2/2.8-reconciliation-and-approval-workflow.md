# 2.8 Reconciliation editor backend and approval workflow

**Status:** ⬜ not started · **Epic:** P2 E09 Approval workflow · **Spec:** ACC07–ACC10, WF01–WF05, §13.2 roles, §14.2 `accounting_revisions`, `approval_actions`, `audit_log`, §15.2 period commands, §15.3 atomic reconciliation command, D06 · **Tests:** T32 T33 T34 T35 T36 (+T44 with 2.4, T15/T16 submission gates) · **Depends on:** 2.5

## Goal
Provide the server side of reconciliation — accept/adjust/replace/reject auto candidates, add manual lines with evidence, atomic draft saves, tolerance handling — and the immutable approval lifecycle (Draft → InReview → Approved, Reject, Revise) with separation of duties, content hashes, stale detection, restatement proposals and an append-only audit.

## Spec requirements covered
- ACC07 editor shows target, actual, signed gap, auto candidates, accepted lines, unaccounted, over-accounted, quality exceptions; accept/adjust/replace/reject with reasons; manual lines reference an event, a cause without event, or an approved adjustment; missing code vs missing event distinct.
- ACC08 override = additional revision over candidate; recalculation retains override and alerts if baseline changed; delete override restores candidate after preview; deterministic auto keys.
- ACC09 tolerance default 0 (epsilon 1e-6); site policy may approve % or absolute; residual always stored; within tolerance → labelled tolerance adjustment on acceptance; zero target → absolute tolerance only.
- ACC10 submission fails if over-accounted beyond tolerance, required codes missing, actuals incomplete, recalculation pending, sources conflict; positive residual beyond tolerance needs explanation or explicit approved Unaccounted classification; approval records accepted unresolved classification.
- WF01 lifecycle; Reject → Draft with reason; Approved immutable; Revise → new linked Draft, predecessor published until replacement approved; cancelled drafts auditable; Open/Reconciled labels ≠ workflow state.
- WF02 submit validates versions, policy, coverage, coding, tolerances, permissions in one transaction; content hash; approve requires same hash, different approver, current authz; pre-approval input change → stale.
- WF03 approval snapshot of all inputs; downstream after commit via outbox; delivery failure cannot undo approval.
- WF04 late corrections: draft recalculates; in-review stale; approved → change proposal with before/after; privileged revision with reason, never direct edit; "Unlock" maps to revision.
- WF05 roles/scope on every API/job/export/socket; tenant from identity.
- §15.2 `PUT /production-periods/{id}/draft-lines`, `recompute`, `submit`, `approve`, `reject`, `revise`; §15.3 validation: scope, current run, code compatibility, evidence availability, allocation budgets, decimals → 422 with offending line and remaining allocation; concurrent → 412 + diff.

## Current implementation (verified)
- `reconcile_forms` always `Draft`; update DTO broken (B3); `loss_categories` update DTO broken (B4); save = delete all + recreate (non-transactional); event link dropped (B10); plan approval strings set by client; no audit beyond generic interceptor; `RolesGuard` used on 2 routes.

## Target design
**Schema (migration `0016-workflow`)**
```
accounting_revisions (+ columns): submitted_by, submitted_at, submitted_hash, submitted_run_id, approved_by, approved_at, approval_snapshot_ref, rejected_by/at, reject_reason, cancelled_by/at, is_stale bool, stale_reason, comment
approval_actions: id, tenant_id, revision_id, action enum(submit, approve, reject, revise, cancel, recompute, stale), actor_id, at, reason, submitted_hash, correlation_id
approval_snapshots: id, revision_id, content jsonb (all input revision ids, lines, targets, actuals, schedule, rate & code versions, valuation snapshots, kpis, exceptions, policy versions, submitter/approver/times/comments), content_hash, stored_at   -- immutable, retained per NFR07
period_change_proposals: id, tenant_id, period_id, approved_revision_id, trigger enum(event_change, actuals_change, plan_change, rate_change, calendar_change, source_retraction), before jsonb, after jsonb (preview run totals), affected_reports jsonb, state enum(open, accepted→revision_created, dismissed), created_at, resolved_by/at
audit_log: id, tenant_id, actor_id | service, action, entity_type, entity_id, revision, before_hash, after_hash, reason, correlation_id, at   -- append-only (no UPDATE/DELETE grants)
loss_lines.state += 'rejected_candidate'; manual line fields: evidence_event_revision_ids, adjustment_id, missing_code bool, missing_event bool
```
**Draft lines command** `PUT /production-periods/{id}/draft-lines {revision, baseRunId, lines[], expectedVersion}` (§15.3):
- One transaction: verify revision is `draft` and `current_run_id == baseRunId` (else 409 `RUN_CHANGED` with current run + diff of auto candidates); `row_version == expectedVersion` (else 412 with latest revision); validate each line: scope (slice belongs to period), ledger/kind/basis enum, code versions effective and compatible (`code_mapping_rules`), evidence events exist and overlap the segment (else `missing_event` must be explicit), decimals ≤ 8 dp, allocation budget: Σ accepted plan lines ≤ gap + tolerance unless `kind=bridge/gain` explains it → 422 `{line, expectedRemainingAllocation}`; replace the **full** set of manual/accepted lines for the revision (`state` transitions: candidate accepted → `active`, overridden → `candidate_superseded`, rejected → `rejected_candidate`); recompute totals (`residual`, `over_accounted`, `unaccounted`) via 2.5 totals function **without** a new run; write `audit_log`; return new ETag. Never delete-then-recreate outside the transaction (T33).
- Override semantics (ACC08): manual line stores `overrides_auto_key`; when a later run changes that candidate, the override is kept and flagged `baseline_changed`; `DELETE override` → preview shows restored candidate before applying.
- Tolerance (ACC09): policy `reconciliation_tolerance {mode: zero|percent|absolute, value}`; on `submit`, if `|residual| ≤ tolerance` and residual ≠ 0 → create `tolerance_adjustment` line (labelled) with the exact residual (T32); zero target → absolute only.

**Lifecycle commands**
- `POST …/recompute {reason}` → 202 job (2.5 run) + impact preview.
- `POST …/submit {revision, runId, contentHash, comment}`: gates (ACC10/WF02): run current & validated; actuals coverage = 100 % accepted (or policy gate); no `missing_code` on active lines unless policy allows; over-accounted beyond tolerance → 422; positive residual beyond tolerance → 422 unless an `unaccounted_classified` line exists under policy `allowUnaccountedClassification`; no open source conflicts/review items on evidence events; role `production_engineer+` with unit scope. Compute `submitted_hash` over the approval snapshot content; client-provided `contentHash` must match (prevents submitting a stale view); lifecycle → `in_review`; `approval_actions`, `audit_log`, outbox `PeriodSubmitted`.
- `POST …/approve {submittedRevision, submittedHash, comment}`: `lifecycle == in_review && !is_stale && submitted_hash == body.submittedHash` (else 409 `STALE_SUBMISSION`, T34); approver ≠ submitter (403, T36); role `manager_approver` in scope; store `approval_snapshots` (WF03) and set `approved` (immutable: triggers reject UPDATE on approved rows except `supersedes` links); outbox `PeriodApproved` after commit (delivery retries in 2.9, T39).
- `POST …/reject {submittedRevision, reason}` → `draft`, reviewer feedback preserved.
- `POST …/revise {approvedRevision, reason}` → new `draft` revision `supersedes_id = approved`, copies accepted lines as candidates; approved stays published/visible until the new one is approved; `Unlock` in UI maps here (WF04).
- `POST …/cancel` for drafts (auditable).
- Late corrections (WF04, from 2.5 run orchestration): draft → recomputed (overrides kept); in_review → `is_stale=true, stale_reason`; approved → `period_change_proposals(open)` with before/after totals from a shadow run; accepting a proposal calls `revise`.

**Roles** (`RolesGuard` + scope, 0.4): operator (events only), production_engineer (draft-lines, submit, recompute), manager_approver (approve/reject/revise), reliability_engineer (RCA links), viewer. Legacy roles mapped: Engineer/Analyst → production_engineer; Manager/TenantAdmin → manager_approver; Operator → operator; SuperAdmin/OrgAdmin → all but still not self-approval.

**Compatibility**: v1 `reconcile-forms`/`loss-categories` write routes return 410 with pointer to v2 once 3.5 ships; until then they are read-only views over lines.

## Tests
- **T32 tolerance**: target 1000, residual 0.5, policy 0.1 % → residual shown 0.5; submit creates explicit `tolerance_adjustment 0.5`; ledger closes; no silent zero.
- **T33 atomic save**: inject failure after half the lines → no partial replacement; previous revision intact; ETag unchanged.
- **T34 approval race**: source revision arrives between submit and approve → `is_stale`; approve → 409; recompute + resubmit → approve succeeds with new hash.
- **T35 post-approval correction**: late PI correction on approved period → snapshot unchanged; `period_change_proposals` open with before/after; accept → new draft revision linked; approved still served with `view=approved`.
- **T36 separation of duties**: submitter calls approve via API → 403; different authorized approver → 200; SuperAdmin submitter also denied.
- **T15/T16 gates**: residual 10 at zero tolerance → submit 422 `RESIDUAL_UNEXPLAINED`; over-accounted 10 → 422 `OVER_ACCOUNTED`.
- **T44** (with 2.4): explanation revision doesn't change actuals result id.
- Draft-lines: stale `baseRunId` → 409 with candidate diff; invalid code combo → 422 with line index; evidence event outside segment → 422 unless `missing_event: true`.
- Audit: every command writes `audit_log`; UPDATE/DELETE on `audit_log` fails at DB level.

## Definition of done
- Reconciliation saves are atomic and validated; lifecycle enforced with hashes, immutability, separation of duties, stale detection and proposals; audit append-only; T32–T36 and gate tests green; B3 B4 B10 resolved in evidence.
