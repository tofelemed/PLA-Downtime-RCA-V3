# 2.5 Loss accounting engine and calculation runs

**Status:** ⬜ not started · **Epic:** P2 E08 Accounting engine · **Spec:** ACC01–ACC06, FND03, ACC08 (deterministic auto keys), §14.2 `accounting_revisions` (draft container), `calculation_runs`, `loss_lines`, `loss_line_evidence`, D04 · **Tests:** T15 T16 T17 T28 T30 (+ T37 conservation, T03 allocation) · **Depends on:** 1.1, 1.2, 1.10, 2.2, 2.4

## Goal
Compute, reproducibly and on the server, the two loss ledgers for every production period: the **capacity ledger** (what sustained capacity could have produced) and the **plan ledger** (approved target vs good actual), deriving availability, performance and quality losses from events, states, rates and actuals; allocating them to causes without double counting; and exposing signed residuals instead of fabricated percentages.

## Spec requirements covered
- ACC01 two ledgers with distinct baselines; capacity identity `capacity = exclusion + A + P + Q + good + residual − gains`; plan identity `target − good = attributed + residual`; residual signed, never clamped; overproduction surfaced; attributed plan loss with actual > target flagged; never report negative loss as downtime.
- ACC02 segment at event/schedule/product/rate/measurement boundaries; full stop → sustained rate × non-overlapping stopped time; derate → measured impact or fractional rule; running → ideal gross − gross (above-reference = gain/exception); quality = gross − good (rework policy).
- ACC03 compute once at production boundary then allocate; no adding rate-derived total to event-duration losses; impossible claims fail validation.
- ACC04 time loss may use sustained rate (capacity) and time-phased planning rate (plan) with explicit basis; quantity plans without credible time reference → capacity losses + explicit plan allocation request; never distribute by final gap.
- ACC05 allocations reference event id + revision, unit, product, clipped segment, code versions, basis, run; one event many periods; evidence association; conservation per segment and ledger.
- ACC06 overlaps → primary cause or shares; value-chain boundary; aggregation scope labels.
- FND03 new immutable result set per recalculation, validated, then atomic pointer switch; serialized per period; unchanged input fingerprint → no duplicate active lines.
- ACC08 deterministic keys for auto lines.

## Current implementation (verified)
- Browser only: `PlanDashboard.calculateLosses` (`losses = max(0, planned − actual)`, unaccounted = fabricated 25–40 %), "Calculate from Events" uses a hard-coded fake array (B9); reconcile categories free text; no event ↔ loss link (B10); OEE written by the browser. Nothing server-side.

**Engine** `src/domain/accounting/` (pure decimal functions, then a Nest service orchestrating persistence)
1. **Inputs** (frozen per run): period + slices, `shift_instances` (scheduled/excluded), occurrences and cause allocations (1.10) clipped to the period, event revisions effective at run time, actuals result (2.4), profile rates (sustained + planning versions over time), plan periods, policies (`oee_policy`, `reconciliation_tolerance`).
2. **Segmentation**: boundaries = period edges ∪ shift/exclusion edges ∪ occurrence starts/ends ∪ rate version changes ∪ campaign edges ∪ measurement segment edges → atomic segments.
3. **Capacity ledger per segment**: `c = sustainedRatePerSec × seconds`; excluded segment → `schedule_exclusion = c`; full-stop occurrence → `availability = c` (shares to causes per `cause_allocations`); derate → `availability_or_performance = c × fraction` or measured impact (policy chooses component; default performance for `reduced_rate`); running → `performance = max(0, c − gross_segment)`, `gain = max(0, gross_segment − c)` flagged `above_reference`; `quality = gross_segment − good_segment` (rework per ACT07). Gross/good per segment from actuals source segments or proportional distribution of the slice total over running time (marked `estimated`). **Residual** = `c − exclusion − A − P − Q − good + gain` (signed), one line per slice.
4. **Plan ledger per slice**: `target` from `plan_periods` (Σ over period), `actual = good`; `gap = target − actual`; auto candidate lines mirror capacity A/P/Q lines re-based with `planning_rate` for time losses (`basis=planning_rate`) and declared quantities for Q; `attributed = Σ active plan lines`; `residual = gap − attributed` (signed). If `gap < 0`: `overproduction = −gap`; positive attributed lines → `conflict` flag (T17). Quantity-based plan with no time-phased planning rate → no auto time lines; `residual = gap` + flag `plan_allocation_required` (ACC04).
5. **Conservation checks** (validation before pointer switch): per segment Σ allocation shares = 1; Σ capacity lines = c; plan lines ≤ gap unless flagged; no negative loss quantities except kinds `residual|gain|bridge`; quality ≤ gross; gross ≥ 0.
6. **Deterministic auto keys**: `${ledger}:${kind}:${sliceId}:${segmentStart}:${occurrenceId|'-'}:${causeEventId|'-'}` → re-running produces identical keys; manual lines (2.8) reference `auto_key` they override → candidate becomes `candidate_superseded`, kept for provenance (ACC08).
7. **Run lifecycle** (FND03): `PeriodRecalculateRequested` → acquire advisory lock on period → compute `input_fingerprint`/hash; equal to current run → skip (no new lines); else create run `queued→running`, call `ActualsRunner` (2.4) if actuals inputs changed, compute lines + totals + KPIs (2.7) + valuation (2.6) into the new run, validate, then in one transaction set `accounting_revisions.current_run_id` (draft) and mark the old run `superseded`. In-review revision → mark `stale` (2.8); approved → never touched; proposal created (2.8).

**Compatibility**: view `production_losses_v` (plan ledger totals as `shortRangePlan/actual/losses/unaccountedLoss/action`) and `loss_categories_v` (active plan lines) so the v1 Plan Dashboard shows real numbers until 3.5.

**API v2** (read; commands in 2.8): `GET /production-periods/{id}?revision&view=approved|draft` → both ledgers, lines with evidence, totals, run id, policy versions, `isProvisional`; `GET /production-periods/{id}/runs`.

## Tests
- **T15**: target 1000, actual 850, accepted lines 90+40+10 → gap 150, attributed 140, residual 10; `period_ledger_totals` exact; (submission failure asserted in 2.8).
- **T16**: lines 160 → residual −10, `over_accounted 10`.
- **T17**: actual 1050, attributed 20 → overproduction 50, residual −70, conflict flag; no downtime reported as 70 t.
- **T28**: 8 h calendar, sustained 100 t/h, 1 h excluded, planning 90 t/h → capacity 800, exclusion 100, availability 100 (1 h stop), performance 30, quality 20, good 550, residual 0; plan gap 80 with planning-rate stop candidate 90 → `bridge/conflict` flag, no forced allocation.
- **T30**: stop 30 min @100 then 30 min @120 → capacity availability 110 t across two rate versions (two lines, two `rate_version_id`).
- **T03/T37**: overlapping asset stops → unit availability from occurrence union; allocation shares sum to 1 per segment; split/merge of the evidence events leaves Σ allocated unchanged.
- Determinism: same inputs → same `auto_key`s and quantities; re-run with identical fingerprint creates no run; changed input → new run, old superseded, draft pointer switched atomically (concurrent read sees old or new, never mixed).
- Validation: quality > gross → run `failed` with error; residual never clamped (negative preserved).

## Definition of done

## Decisions / risks
- D04 fixes the default policy for derate component (performance) and planned stops (reduce availability inside schedule).
- Segment-level gross/good needs measurement segments; when only slice totals exist, proportional distribution is marked `estimated` — acceptable per ACT02 only under policy.
- Engine performance: ordinary period recompute target p95 < 60 s (§17.1); segmentation is O(boundaries); measure in 3.11.
